# 密钥与渠道授权规范

> 状态：目标授权规范。当前管理面已有 `channels/models` 字段和多选 UI，但后端 registry
> 仍是 bridge 实现；渠道启用语义、模型交叉校验、alias 授权和无源项目验收必须按本文补齐。

## 1. 对外承诺

调用方只配置一个 Gateway Base URL 和一把 All2API Key：

```http
GET  https://gateway.example/v1/models
POST https://gateway.example/v1/chat/completions
Authorization: Bearer sk-a2a-...
```

调用方不需要知道平台客户端、浏览器 worker、账号凭据或渠道内部地址。模型使用 `<channel>/<model>` 明确指定渠道，也可以使用管理面配置的 alias；alias 不能绕过 Key 授权。

## 2. Key 数据模型

```json
{
  "name": "team-a",
  "channels": ["wb", "chatgpt"],
  "models": ["wb/glm-5.2", "chatgpt/gpt-4o-mini"],
  "limit_rpm": 60,
  "expires_at": null
}
```

字段规则：

- `channels` 允许一个或多个已注册渠道；空数组表示全部**已启用且已配置**渠道，不表示未来自动授权未知平台；
- `models` 允许完整模型 ID、渠道前缀模型 ID 或 `*`；空值按 API schema 规范化为 `[*]`；
- 模型 scope 必须与 channel scope 交叉校验。`channels=[wb]` 时不得保存 `chatgpt/...`；
- 如果只需要单渠道，UI 选择一个即可，不需要创建多把 Key；
- Key 在管理员列表中以脱敏值展示并支持显式复制；数据库只保存用于鉴权的 hash，以及由服务主密钥保护的当前 Key 密文，不保存未加密明文。viewer 只能看到 prefix 和安全元数据；历史旧 Key 若没有密文必须轮换后才能复制；
- bootstrap Key 由服务端配置初始化，不能通过管理 API 编辑、轮换或撤销。

## 3. 管理 API

### 创建

```http
POST /admin/api/keys
```

```json
{
  "name": "workbuddy-client",
  "channels": ["wb"],
  "models": ["wb/*"],
  "expires_at": null,
  "limit_rpm": 120
}
```

响应 `201`：

```json
{
  "data": {
    "id": 12,
    "name": "workbuddy-client",
    "prefix": "sk-a2a-abc",
    "channels": ["wb"],
    "models": ["wb/*"],
    "enabled": true
  },
  "key": "sk-a2a-..."
}
```

必须返回 `Cache-Control: no-store`。列表、编辑和审计永远不返回完整明文。

### 编辑/轮换/撤销

- `PATCH /admin/api/keys/{id}`：修改名称、channels、models、RPM、到期和 enabled；重新执行完整 scope 校验；
- `POST /admin/api/keys/{id}/rotate`：旧值立即失效，新值只返回一次；
- `DELETE /admin/api/keys/{id}`：软撤销，保留审计和请求关联；
- 创建、scope 变更、轮换、撤销均写 `key.created/key.updated/key.rotated/key.revoked` 审计事件。

## 4. 数据面授权算法

```text
解析 Bearer/x-api-key
  → 哈希匹配、enabled/expiry/RPM/IP 检查
  → 规范化 model（channel/model 或 alias）
  → alias 展开为有序目标
  → 对每个目标检查 channel scope + model scope
  → 只把获授权目标交给 scheduler
  → 记录 key_id、实际 channel/model、fallback_depth
```

规则：

1. 未授权渠道返回统一 `403 channel_not_allowed`，不得尝试该渠道或把请求静默改投其他渠道。
2. 未授权模型返回 `403 model_not_allowed`；模型不存在返回 `404 model_not_found`，不要用 403 隐藏配置错误。
3. alias 中所有目标都未授权时返回 403；部分目标未授权时直接过滤未授权目标，并在审计/调试日志中记录过滤原因，不把未授权目标发给 adapter。
4. Key 的渠道授权与管理员会话角色无关；管理面 Cookie 不能调用 `/v1`。
5. `/v1/models` 只返回该 Key 可见的模型；不能先返回全量再由客户端过滤。

## 5. 渠道和模型命名

推荐：

```text
wb/cn:glm-5.2
doubao/doubao-pro
chatgpt/gpt-4o-mini
```

适配器负责剥离渠道前缀并转换平台模型名；核心只比较 canonical ID。禁止用展示名称、模糊后缀或不稳定别名作为授权依据。路由 alias 必须声明目标渠道和模型，保存时校验目标存在或允许处于 `pending` 状态并在调用时再次校验。

## 6. 安全要求

- 使用常数时间比较和强随机生成 Key；
- 日志只写 prefix、key_id 和 hash 关联，不写 Authorization header；
- 前端内存中展示明文后，关闭/刷新即丢失，不写 localStorage、URL、错误追踪或剪贴板历史（复制是用户显式动作）；
- Secret、上游凭据、账号 token 和浏览器 Cookie 与 Gateway Key 完全分离；
- 轮换/撤销是原子操作，已有请求可完成但新请求必须立即按新状态校验；
- 管理 API 的写操作需要 admin、CSRF/Origin 检查和审计；viewer 只能读取脱敏元数据；
- 导出、备份和 support bundle 默认排除 Key hash 以外的敏感内容。

## 7. 与账号/渠道生命周期的关系

渠道禁用时，已有 Key scope 不被静默扩大；请求返回 `503 channel_disabled`，管理员可以在编辑 Key 时调整范围。删除渠道前必须：停用其模型和路由目标、撤销/迁移相关 Key、销毁凭据、保留审计摘要。

新增渠道注册后不会自动获得已有 Key 的显式授权；只有 `channels=[]` 的“全部当前已启用且已配置渠道”Key 才按策略获得它，且系统应在审计/变更摘要中提示授权面扩大风险。高安全部署可以将空数组解释为当前快照并要求管理员确认扩展，配置项需在发布前固定，不能两种语义并存。

## 8. 测试和验收

必须覆盖：

- 单渠道 Key 调用正确渠道成功，跨渠道 403；
- 多渠道 Key 使用同一 `/v1` 调用三渠道成功；
- `channels=[]`、`models=["*"]`、渠道前缀、alias 的组合；
- alias 中未授权目标不会被尝试，fallback 深度和日志正确；
- 过期、禁用、RPM 超限、轮换、撤销和并发更新；
- `/v1/models` 与实际授权一致；
- 响应、日志、SQLite dump、前端 bundle 不含完整 Key 或上游 Secret。
