# 企业开发规范

本文是 All2API 的研发和评审门禁。目标是让后续开发者能在不了解三个源项目细节的情况下，按统一边界增加能力。

## 1. 目录和依赖

后端是单一 Go 模块（`github.com/XuLaiQ/all2api`）：

```text
cmd/
├─ all2api/                # 网关 + 管理面；在 main.go 装配依赖
├─ doubao-browser-worker/  # Chromium/CDP worker
└─ media-worker/           # 媒体处理 worker
internal/
├─ domain/                 # 纯业务规则（如 scope）
├─ application/            # 用例服务和事务编排（accounts、gateway、keys、media…）
├─ ports/                  # 稳定的抽象接口
├─ adapters/               # 每渠道独立包 + registry（含 fake 测试适配器）
├─ infrastructure/         # persistence(SQLite+migrations)、crypto、media、security、tokens
├─ transport/http/         # HTTP 入站，按领域拆分 handler 文件
├─ scheduler/              # 账号池和租约
├─ protocols/              # Anthropic/Responses 协议转换
├─ browser/                # 浏览器 worker 与 CDP
└─ config/                 # A2A_* 与 .env 加载、校验
tools/                     # 仓库维护工具（doclinks、supplychain）
```

测试与实现同包（`*_test.go`）。数据库 schema 位于 `internal/infrastructure/persistence/migrations/`。文档中的目录必须和实际提交同步，不能引用不存在的包作为已实现事实。

依赖方向固定为：

```text
transport/http → application → domain
                     ↓
                   ports ← adapters / infrastructure
```

`cmd/all2api/main.go` 是唯一装配点。反向 import、循环依赖、handler 直接拼 SQL 或调用平台 HTTP、domain 依赖 HTTP/SQLite 均视为评审阻断项。

## 2. 命名和接口

- Go 代码遵循 `gofmt` 和 Effective Go：包名小写单词，导出标识符 `PascalCase`，非导出 `camelCase`；文件名小写，测试文件 `*_test.go`；
- 脚本与工具目录使用小写 kebab-case（如 `verify-go-build.ps1`）；渠道 slug 使用小写 ASCII；
- TypeScript 类型与组件使用 `PascalCase`；HTTP JSON 字段统一 `snake_case`；
- `channel` 指稳定 slug，`adapter` 指实现，不混用 display name；
- 方法名表达副作用：`List*` 不写入、`Refresh*` 才可访问平台并更新单个账号状态、`Import*`/`Provision*` 会写凭据；不新增账号列表同步接口；
- 所有跨层输入先通过具名 struct 校验，禁止以 `map[string]any` 穿透整个系统；
- 所有 I/O 函数第一个参数是 `context.Context`，禁止使用全局可变 session。

## 3. 配置和 Secret

- 配置 schema 必须版本化，并在启动时校验必填项、范围和互斥项；
- 目标态配置描述内置 adapter/client/worker，不要求旧源项目的 URL、端口、token 或数据库；
- Secret 只保存在 `config.Config` 的进程内字段中，禁止用 `%v`/`%+v` 打印配置，禁止写入日志和错误响应；
- 环境变量只在 `internal/config` 中读取（含 `.env` 加载），不在 domain/application 直接调用 `os.Getenv`；
- `*.env`、账号数据、Cookie、浏览器 profile、运行态和本地数据库不得提交；
- 变更 Secret/凭据格式必须写迁移和回滚说明，旧值不能在异常中回显。

## 4. 数据库和迁移

- 每个 schema 变更有单独递增版本、前向脚本、验证和必要的回滚/备份说明；
- 迁移可重复执行，启动前检查 schema version，禁止运行时静默创建不受控列；
- 凭据表只保存加密密文或引用；Key 只保存哈希；平台特有字段使用版本化 JSON；
- 所有写操作明确事务边界、幂等键、唯一约束和并发冲突行为；
- 删除渠道/账号前先处理外键、Key、路由、凭据和审计；
- 生产迁移必须先备份并在临时副本演练，不能用 `DROP TABLE` 代替迁移。

## 5. HTTP 和日志

- API 契约先更新 `docs/API契约.md` 与 OpenAPI，再改实现和前端；
- 管理 API 使用统一 envelope、错误码、request_id、分页和 UTC 时间；
- 数据面错误遵循目标协议，SSE 不缓存、不缓冲，流开始后不重放；
- 日志结构化记录 request_id、channel、model、status、error_kind、latency、usage；
- 禁止记录 Authorization、Cookie、OAuth callback、token、profile 路径、上游原始错误体和完整 IP/UA（除非安全策略明确且脱敏）；
- 健康检查区分 `config_missing`、`adapter_unavailable`、`platform_unavailable`、`credential_expired`，不要只返回一个“正常/异常”。

## 6. 测试门禁

最低门禁：

```powershell
gofmt -l cmd internal tools
go vet ./...
go test ./...
pnpm --dir web lint
pnpm --dir web typecheck
pnpm --dir web build
go run ./tools/doclinks
```

按风险补充：

- domain/application：纯单元测试，覆盖边界和并发（必要时 `go test -race`）；
- adapter：`httptest` mock 上游契约测试，禁止 CI 调真实账号；
- provisioning：每种 flow 的状态机、幂等、取消、过期、重试和凭据不泄露；
- security：Key scope、同源写保护、权限、日志脱敏、密钥轮换；
- integration：临时 SQLite、迁移、事务，以及 `route_coverage_test.go` 的路由契约覆盖；
- E2E：登录、选择渠道新增账号、Key 创建、各渠道调用和拒绝路径（`scripts/probe/`，不进入普通测试）。

## 7. CI、依赖和供应链

CI 必须执行：

1. gofmt/vet/test 与 Web lint/typecheck/build；
2. `go mod verify`、`go run ./tools/supplychain`、govulncheck、go-licenses 和 SBOM（`scripts/ops/generate-go-sbom.ps1`）；
3. `rg` 检查运行时代码不得出现 `F:\token-p`、源项目 import、旧端口和未批准 bridge；
4. 构建镜像/产物检查不得包含账号数据、浏览器 profile、`.env` 或 Secret；
5. 从空缓存 clean checkout 构建，验证不读取工作区外路径。

复制或重写源代码前，必须记录来源仓库、提交/版本、文件/函数、许可证、修改范围和测试 fixture。许可证不清晰时停止迁移并提交法务/负责人评审。

## 8. 分支、提交和评审

- 默认分支保护；功能分支使用 `codex/<topic>` 或团队约定前缀；
- 一个提交聚焦一个可回滚主题，提交信息说明模块和行为变化；
- PR 必须包含：需求编号、架构/契约/DB 影响、迁移来源、风险、测试命令、截图或 API 示例；
- 至少一名后端 reviewer 审 adapter/凭据/数据库，至少一名 Web reviewer 审动态 schema/权限状态；
- 未完成的迁移用 feature flag 隔离，不能以 TODO 代替边界；
- 任何新增平台必须证明通用核心没有平台分支，或附 ADR 解释例外。

## 9. 安全和运维评审

发布前检查 HTTPS、可信代理、CORS、Cookie 属性、备份恢复、日志保留、告警、限流、浏览器 worker 资源和凭据轮换。生产环境不得使用默认 session secret、弱管理员密码、`any` API key 或调试 traceback。

## 10. 变更检查表

```text
[ ] 需求/验收编号已关联
[ ] domain/application/ports 边界正确
[ ] 新渠道只改 adapter + registry + 配置 + 测试
[ ] API 契约/routes.json/前端 DTO/文档同步
[ ] migration、幂等、审计、回滚已说明
[ ] Secret/源路径/源端口扫描通过
[ ] gofmt、vet、go test、lint、typecheck、build 通过
[ ] verify-go-clean-build 在临时目录构建并启动通过
```

## 11. 当前快照与文档治理

Go 是唯一后端运行时：四渠道 native provisioner、二维码状态机、Fernet 凭据存储和本地账号目录已实现；Python 后端、legacy bridge 和 `A2A_LEGACY_*` 配置已删除（生产环境拒绝这些变量）。
提交信息或 README 的目标描述不能替代代码实测；只有真实平台 E2E 通过后，才可以把渠道标记为已验收。

每次 adapter、provisioner、manifest、Key scope、账号流程、路由或数据库变更，PR 必须同步更新：

1. [统一平台整合需求说明](统一平台整合需求说明.md) 中受影响的 REQ 和完成证据；
2. 复制或改写外部代码时的来源、许可证和状态；
3. [API 契约](API契约.md)、`docs/migration-baseline/routes.json`、前端 DTO、`.env.example` 和部署说明；
4. 对应的契约/集成/安全测试和 E2E 记录。

文档中的 `[目标/待实现]`、`[实测]` 标记必须保留。若文档与代码不一致，先修正文档中的状态，再提交实现；不得用“计划目录”描述尚未存在的代码。
