## 1. 系统定位与总体架构

### 1.1 三个源系统的真实形态 `[实测]`

审计结果与最初设想有出入，**必须先把事实摆清楚**，否则架构会建在错误前提上：

| 维度 | WorkBuddy `wb2api` | 豆包·千问 `doubao2api` | ChatGPT `chatgpt2api` |
|---|---|---|---|
| **项目路径** | `F:\token-p\WorkBuddy\wb2api` | `F:\token-p\反代\doubao2api` | `F:\token-p\chatgpt2api` |
| **运行时** | **双进程**：FastAPI `:7864` + **Go 网关** `:7863` | 单进程 FastAPI `:9090` | 单进程 FastAPI `:8000`（容器 `:80`） |
| **核心逻辑位置** | 账号池/选号/冷却/转发**全在 Go 侧**；Python 只管管理面 + 协议翻译 | 全在 `src/server/unified_server.py`（2831 行单文件） | 分散在 `services/account_service.py`（78KB）+ `openai_backend_api.py`（129KB） |
| **上游访问方式** | Go 直连 HTTP | **Playwright 在页面内 `fetch()`**，靠页面 hook 自动加 `a_bogus`/`msToken` 签名 | **纯 HTTP + `curl_cffi`** 指纹伪装，Python 内实现 PoW / Turnstile / Sentinel |
| **账号凭据形态** | 文件 `data/auths/workbuddy*.json`（嵌套/扁平两种格式） | 目录 `data/accounts/<id>/meta.json` + Chromium profile | `data/accounts.json`（OAuth 三件套 access/refresh/id_token） |
| **账号状态** | Go 侧 `entry` 结构体**运行时派生**，`state.json` 只存原始维度 | `Account.status` 是**派生属性**（`status_override` 优先） | 4 个**中文字符串字面量**散落各处，无枚举类 |
| **状态取值** | 派生自 `disabled`/`manualDisabled`/`cooling`/`degrade_until`/`breaker_until` | 7 值枚举 `unknown/ready/busy/need_login/cooldown/captcha/error` | `正常/限流/异常/禁用` |
| **选号策略** | 三因子加权 Top5 短名单 → 加权随机 → LRU 兜底 + 成本分层 | `least_connections` / `round_robin`（`priority` **不参与**） | 图片/文本轮询；PPT/PSD 按 `last_used_at` LRU |
| **并发字段** | `Acquire`/`Release` 租约，上限按 realm 分档 | `max_concurrent`（默认 1） | `config.image_account_concurrency`（默认 3） |
| **持久化** | SQLite `manager.db` **13 张表** + `state.json` | 账号**纯文件+内存**（重启丢运行态）；SQLite 只服务 Playground | 可插拔存储：`json`/`sqlite`/`postgres`/`git` |
| **多模态** | 仅对话 | 图像 / 视频 / 音频 / 文件 | 图像 / 检索 / PPT / PSD |
| **鉴权** | 三套：数据面 `wbk_`、管理面 `wbt_`、Go 入站 `api_key` | 单一 `DOUBAO_API_KEY`（支持字面量 `any`）+ 内存 Session Cookie | `CHATGPT2API_AUTH_KEY` + 用户密钥（SHA-256） |

> **最容易搞错的三点**（写文档/写代码时都要注意）：
> 1. `wb2api` **不是**"Python 后端 + 前端"，它有个 **Go 反代网关**，账号池逻辑全在那里；
> 2. `doubao2api` 的 `priority` 字段**存得下、显示得出，但不影响选号**（`account_manager.py:295-299` 的排序 key 里没有它）；
> 3. `chatgpt2api` 的 `quota` **不是「次/3h」**，它是上游 `image_gen.remaining`，
>    恢复时间由上游 `reset_after`（落为 `restore_at`）决定，代码里没有任何 3 小时窗口常量。

### 1.2 形态判断：为什么是「单项目内置适配器 + 统一网关」`[设计]`

三个源系统**都已经各自暴露 OpenAI 兼容 HTTP 接口**：

```
wb2api     POST /v1/chat/completions  /v1/messages  /v1/responses     :7864
doubao2api POST /v1/chat/completions  /v1/images/generations  ...     :9090
chatgpt2api POST /v1/chat/completions /v1/responses /v1/messages ...  :8000
```

这些事实只说明迁移时要隔离三种技术边界，不意味着继续依赖源项目。三种形态的对比：

| 形态 | 做法 | 结论 |
|---|---|---|
| A. 原样代码拼接 | 把三份 server/router/database 直接合并 | ✗ 依赖、生命周期、凭据边界和数据模型冲突 |
| B. 各自独立，加一个配置化 nginx | 纯静态反代 | ✗ 拿不到统一管理：账号状态、冷却、配额、日志各自为政，无法跨渠道降级 |
| 迁移期 bridge | 网关通过 HTTP 调用三个源项目 | 仅用于行为对照和过渡；M0 的目标开关默认关闭，不计入最终验收 |
| **C. 单项目内置适配器** | 将协议、账号流程、凭据和平台 client/worker 重构进 `adapters/<slug>`，经 ports 接入统一核心 | ✓ **目标态采用** |

**C 的关键设计**：网关不调用源项目管理接口，而是通过 registry 调用本项目的
`UpstreamAdapter` 与 `AccountProvisioner`。这样：

- 上游逻辑变更**只影响适配器**，不影响网关核心；
- 浏览器类渠道的 Playwright 进程、平台专用 worker 可以留在**本项目内部**，故障隔离；
- 网关可以用**统一策略**（优先级、加权、降级）跨渠道调度，因为它手里有全部渠道的账号视图。

### 1.3 分层架构 `[设计]`

```
┌──────────────────────────────────────────────────────────────────┐
│ L5 接入层                                                         │
│   OpenAI / Anthropic / Responses 三种入站协议 · SSE 流式 · CORS    │
├──────────────────────────────────────────────────────────────────┤
│ L4 管控层                                                         │
│   鉴权(Key) · 授权(渠道/模型白名单) · 限流 · 配额 · 审计           │
├──────────────────────────────────────────────────────────────────┤
│ L3 调度层                                                         │
│   路由解析(别名→渠道链) · 选号 · 冷却/熔断 · 重试/降级 · 会话粘性   │
├──────────────────────────────────────────────────────────────────┤
│ L2 适配层  ★核心★                                                 │
│   registry · manifest · UpstreamAdapter · AccountProvisioner         │
├──────────────────────────────────────────────────────────────────┤
│ L1 计量层                                                         │
│   请求日志 · 用量聚合 · 账号级回填 · 指标                            │
├──────────────────────────────────────────────────────────────────┤
│ L0 存储层                                                         │
│   SQLite(元数据+日志+用量) · state.json(账号运行态) · 密钥哈希      │
└──────────────────────────────────────────────────────────────────┘
        │                    │                    │
        ▼                    ▼                    ▼
  adapters/workbuddy   adapters/doubao       adapters/chatgpt
  (+ optional worker)  (+ browser worker)    (+ HTTP/fingerprint client)
```

**为什么调度层在 L3、适配层在 L2**：调度策略（选哪个渠道、哪个账号）是**跨渠道的统一决策**，
必须在适配层之上；而"怎么把请求翻译成这家上游能懂的格式"是**渠道私有知识**，必须封在适配器里。
这条边界决定了新增平台时改动量的上限。

### 1.4 进程与端口拓扑 `[设计]`

```
                    ┌─────────────────────────────┐
   客户端 ──────────►│  all2api-gateway            │
   (统一 url+apikey) │  FastAPI + uvicorn          │
                    │  :8080  对外 + 管理面        │
                    └──────┬──────────┬───────┬───┘
                           │          │       │
              ┌────────────┘          │       └────────────┐
              ▼                       ▼                    ▼
              ┌──────────────────┐   ┌────────────────────┐  ┌──────────────────┐
              │ WorkBuddy adapter │   │ Doubao adapter      │  │ ChatGPT adapter  │
              │ optional worker   │   │ browser worker      │  │ client/worker    │
              └──────────────────┘   └────────────────────┘  └──────────────────┘
              （代码、镜像、生命周期均由本仓库管理）
```

**目标部署只有一个 All2API 交付物**：内部 worker 可以独立进程以隔离浏览器或平台
专用依赖，但由本仓库的镜像、Compose、配置和健康检查管理。不得把 `upstream_base`
指向三个源项目；官方平台地址属于 adapter 自己的配置。

### 1.5 技术栈选型 `[设计]`

| 层 | 选型 | 理由 |
|---|---|---|
| 语言/框架 | **Python 3.13 + FastAPI + uvicorn** | 统一核心运行时；平台差异通过 ports 隔离 |
| HTTP 客户端 | **httpx**（异步） | 三家都在用；原生支持 SSE 流式与超时分级 |
| 存储 | **SQLite**（WAL 模式） | 单机运维场景够用；wb2api 已验证 13 张表 + 裸 SQL + 自研迁移在真实流量下可行 |
| 账号运行态 | **JSON 文件 + 内存** | 高频读写、需要原子落盘；放 DB 会引入无谓的事务开销 |
| 前端 | 见 `docs/前端开发准备.md` 与 `design/README.md` | 视觉与工程约定分开维护 |
| 部署 | **单一交付物**，可含受控内部 worker | 浏览器类渠道需要独立资源/进程边界，但不依赖外部源项目 |

> **不引入的组件**：Redis / 消息队列 / ORM / 微服务框架。
> 理由：单机运维工具，请求量级是"每秒几十"而非"每秒几万"。
> 源项目的实现只作为行为和风险参考；目标代码必须通过本项目的 ports、迁移和安全门禁。

## 2. 关键设计决策（ADR）

### ADR-1 · 源项目零运行依赖，渠道逻辑内置

**决策**：将三个源项目中的可迁移协议、账号、调度和凭据行为重构到本仓库的
`adapters/<slug>`、`ports` 和受控 worker；All2API 不通过 HTTP、进程、文件或数据库
依赖源项目。迁移期间允许一个默认关闭的 legacy bridge 做对照。

**理由**：
1. 三种访问机制（Go 账号池、Playwright 持久化上下文、指纹 HTTP/OAuth）依赖树和
   生命周期不同，必须在 adapter/worker 边界隔离，而不是把三个 server 原样拼接 `[实测]`；
2. Doubao 每个账号可持有 Chromium persistent context，浏览器崩溃应隔离在本项目 worker，
   不能把外部服务当作故障边界；
3. 官方平台接口随时会变，适配器隔离、契约测试和版本化 manifest 让影响面可控。

**代价**：需要迁移、重写和维护三套平台专有依赖，并为浏览器/worker 设计资源隔离。

---

### ADR-2 · 渠道 = 可插拔适配器

**决策**：每个平台实现一个适配器包，声明 `ChannelManifest`、`UpstreamAdapter` 和
`AccountProvisioner`；注册到 registry 即生效。管理面只调用通用 application service。

**理由**：这是「架构上支持持续新增平台」这一目标的唯一可落地形式。
如果新增平台需要改网关核心代码或数据库表结构，可扩展性就是空话。

**判据**：新增一个平台后，以下位置**必须零改动**——
渠道列表、账号表、日志表、统计维度、路由目标选择器、调试台渠道下拉。
它们全部按适配器注册表动态渲染 `[设计]`。

---

### ADR-3 · 平台差异走 `ext{}` 扩展字段，不硬塞统一字段

**决策**：统一字段只承载**能跨渠道比较**的语义；渠道特有信息原样放进 `ext{}` JSON 列透传。

**理由**：三家能力差异极大 `[实测]`：

| 能力 | wb2api | doubao2api | chatgpt2api |
|---|---|---|---|
| 额度模型 | `credits` + `quota`/`quota_credit` | **无额度概念** | `quota`（上游 image_gen 剩余） |
| 优先级 | 无 | `priority`（**不参与调度**） | 无 |
| 代理 | 无 | 无 | `proxy`（账号级） |
| 套餐 | `realm`(cn/global) | 无 | `type`(Plus/Pro/Team) |
| 浏览器 | 无 | `browser_data` 路径 | `fp` 指纹覆盖 |

若取并集硬塞：chatgpt2api 的账号会出现 `credits=0`、`priority=0` 这类**假值**，
界面上无法区分"真的是 0"和"这个概念不存在"。
若取交集：会丢掉 wb2api 已有的密钥白名单/双额度/统计能力。

**所以**：统一层定义**完整**的归一化模型，差异用 `ext{}` 保留，
界面上用「按会话计」「不限额」这类**明确文案**表达"不适用"。

---

### ADR-4 · 统一状态机收敛为 8 态

**决策**：三家状态值映射到 8 个统一状态，每个状态附带「处理建议」。

| 统一状态 | wb2api 来源 `[实测]` | doubao2api 来源 `[实测]` | chatgpt2api 来源 `[实测]` |
|---|---|---|---|
| `ready` | `healthy` 且未冷却 | `ready` | `正常` |
| `busy` | `in_flight > 0` | `busy`（`active_requests>0 or active_tasks>0`） | `image_inflight > 0` |
| `cooldown` | `now < until \|\| breaker_until \|\| degrade_until` | `is_cooldown()`（`cooldown_until`） | — |
| `limited` | `modelCooldowns[model]` 未过期 | — | `限流`（`quota==0`） |
| `needLogin` | `invalid_reason` 非空 / 文件缺 `accessToken` | `need_login` | `异常`（`last_refresh_error`） |
| `expired` | `now >= auth.expiresAt` | — | — |
| `error` | `err_total` 持续增长 | `error` / `captcha` | `异常` |
| `disabled` | `disabled \|\| manualDisabled` | `not enabled` | `禁用` |

**必须区分 `cooldown` 与 `limited`** `[实测]`：
前者是**账号级**熔断（连续失败 N 次触发），后者是**模型级**限流
（wb2api 的 `rate_limited_models[]` 精确到模型，doubao 的 6004 错误码，chatgpt 的 `quota==0`）。
合并会丢掉「换一个模型就能用」这个关键信息。

**`captcha` 单独成态**：doubao2api 有独立的验证码状态
（`710022004` → `_needs_captcha`，需人工过验证），它既不是 `needLogin` 也不是 `error`，
处理动作不同（前者要重新登录，后者要过人机验证）`[实测]`。

---

### ADR-5 · 调度策略归一到核心侧，adapter 只做执行

**决策**：All2API 核心自己做选号与降级决策，通过 adapter/worker 把"用哪个账号"
传给官方平台客户端；adapter 不决定跨渠道路由。

**理由**：三家的选号策略差异大且各有短板 `[实测]`：

| 上游 | 现有策略 | 短板 |
|---|---|---|
| wb2api | 三因子加权 Top5 + 加权随机 + LRU | 策略最完善，但**只在渠道内有效**，无法跨渠道降级 |
| doubao2api | `least_connections` / `round_robin` | `priority` 字段**存在但不参与调度** |
| chatgpt2api | 轮询 / LRU | 无优先级概念，无权重 |

统一后的策略（§6.3）：**加权评分 → 候选短名单 → 加权随机 → 冷却兜底**，
评分因子跨渠道一致（健康度、在途、近期成功率、额度余量、冷却剩余）。

**代价**：网关需要知道每个渠道的账号清单与实时状态。账号清单由本项目的
provision 流程写入本地数据库，实时状态由网关运行态维护；目标态不轮询三个源项目的
管理接口。

### ADR-6 · 协议转换放在网关，不放在适配器

**决策**：入站协议（OpenAI / Anthropic / Responses）的统一由网关的协议层处理，
适配器只处理"OpenAI 形状 → 这家上游"的翻译。

**理由**：wb2api 已经验证了这个分层是可行的 `[实测]`——
它的 `routers/anthropic.py` 与 `routers/responses.py` **只做协议双向翻译**，
鉴权/IP/配额/限流/日志/记账全部复用 `routers/gateway.py` 的既有实现
（`anthropic.py:18-26`、`responses.py:11-13` 的注释明确写了这个设计）。

网关只需处理 **1 种标准形状（OpenAI）→ N 个适配器**，
而不是 N×M 的协议组合。Anthropic 与 Responses 的支持只需写一次。

---

### ADR-7 · 浏览器类能力内部隔离 + 健康巡检

**决策**：Doubao 这类依赖 Playwright 的渠道可使用本仓库管理的独立 browser worker，
网关侧只做健康探测与故障隔离（连续失败 → 渠道级降级）。该 worker 不是外部源项目。

**理由** `[实测]`：
- doubao2api 的 `_browser_watchdog()` 每 30s 巡检，`is_alive()` 失败且账号非 busy 时 `restart()`
  （`unified_server.py:423-449`）——**自愈逻辑已经存在**，网关不需要重复实现；
- 但它的 `_ready=False` 熔断阈值是**客户端级 5 次连续失败**（`browser_client.py:126-128`），
  与账号池级的 3 次阈值（`account_manager.py:135-139`）是两套独立计数，容易不同步。

**网关侧的处理**：把该渠道整体标记为 `degraded`，路由跳过它，
但**不停止探测**——一旦恢复立即重新纳入。这比让请求一次次撞上去再超时好。

---

### ADR-8 · 密钥与账号凭据分离

**决策**：网关的对外密钥（`sk-a2a-*`）与上游账号凭据是**两套完全独立的东西**。

**理由**：审计发现 wb2api 有三套凭据，混用会出安全问题 `[实测]`：

| 凭据 | 前缀 | 用途 | 泄露后果 |
|---|---|---|---|
| 数据面密钥 | `wbk_` | 客户端调用 `/v1/*` | 可消耗额度 |
| 管理面令牌 | `wbt_` | 脚本调用 `/api/*` | **可改配置、删账号** |
| Go 网关入站 | `api_key` | FastAPI → Go | 可绕过管理面直接调上游 |

网关只对外暴露**一套**数据面密钥（`sk-a2a-*`），
管理面使用独立的会话 Cookie / 管理令牌，且管理令牌**不允许**用于数据面（反之亦然）。

### 3.3 统一状态机实现 `[设计]`

```python
class AccountStatus(str, Enum):
    READY     = "ready"      # ok      · 不阻塞 · 可正常承接请求
    BUSY      = "busy"       # info    · 不阻塞 · 正在处理请求
    COOLDOWN  = "cooldown"   # warn    · 阻塞   · 连续失败触发，到期自动恢复
    LIMITED   = "limited"    # warn    · 阻塞   · 模型级限流，等待重置或切账号
    NEED_LOGIN= "needLogin"  # err     · 阻塞   · 凭据失效，需重新登录
    EXPIRED   = "expired"    # err     · 阻塞   · 凭据过期，需重新授权
    ERROR     = "error"      # err     · 阻塞   · 最近调用持续失败
    DISABLED  = "disabled"   # neutral · 阻塞   · 已手动停用

ADVICE = {
    "ready":      "可正常承接请求",
    "busy":       "正在处理请求，属正常状态",
    "cooldown":   "连续失败触发冷却，到期自动恢复",
    "limited":    "该模型被上游限流，等待重置或切账号",
    "needLogin":  "凭据失效，需重新登录或导入新 Token",
    "expired":    "凭据已过期，需重新授权",
    "error":      "最近调用持续失败，建议测活后处理",
    "disabled":   "已被手动停用，不参与调度",
}
```

**派生优先级**（`status_override` 最高）：

```
1. status_override 非空        → 用它（人工置位）
2. 凭据缺失/失效                → needLogin
3. 已过期                       → expired
4. 手动/系统禁用                 → disabled
5. 账号级冷却未到期              → cooldown
6. 该模型在模型级冷却中           → limited
7. 在途请求 > 0                 → busy
8. 否则                        → ready
```

> 这个顺序是照 doubao2api 的 `Account.status` 派生属性
> （`account_models.py:63-75`）扩展而来——它已验证了「override 优先 + 逐级降级」
> 这个模式在真实运行中够用。

### 4.2 接口设计的三条约束 `[设计]`

**(1) `probe` 必须接受 `native_ids` 列表，不允许无参调用。**

这是从源项目的真实缺陷反推的 `[实测]`：doubao2api 的
`POST /admin/api/probe`（`unified_server.py:2480-2496`）**不读取任何参数**，
内部直接 `await _acquire_account()`（不传 `request`），
于是"全部测活"实际只测了调度器任选的**一个**账号。界面文案与作用域不一致，结果误导。

→ 统一接口强制批量语义：`probe(cfg, native_ids: list[str])`。

**(2) `login_flow` 必须显式建模四态，不允许"一直转圈"。**

`[实测]` 原豆包界面读 `result.qr_image`，而后端返回的是 `qr_image_base64`
（`unified_server.py:2691,2695,2733`），字段名不匹配导致**二维码根本不显示**，
用户只能看到一直转圈。

→ 统一建模：

```python
class LoginFlow(BaseModel):
    state: Literal["idle", "fetching", "awaiting", "expired", "confirmed", "failed"]
    qr_image_base64: str | None = None
    expires_at: int | None = None
    account_id: str | None = None
    message: str | None = None
```

四态显式渲染，`qr_image_base64` 是**唯一约定字段名**，适配器负责把上游的
任意字段名（`qrcode` / `qr_image` / `qr_url`）映射到它。

### 4.4 三个内置适配器的迁移要点 `[实测 + 设计]`

以下表格保留源项目事实，表示**要迁移的行为**，不是目标运行拓扑。目标实现必须放入
`adapters/<slug>`，通过本项目 ports 访问官方平台或内部 worker；不得请求源项目端口、
读取其文件或调用其管理 API。完整文件/函数映射见[三渠道代码迁移矩阵](三渠道代码迁移矩阵.md)。

#### `wb` 适配器

| 项 | 实现 |
|---|---|

> 2. `temperature` **完全未被消费**（全仓仅 `unified_server.py:272` 一处声明）；

> 3. 账号运行态**不落盘**，重启即丢——`meta.json` 只存 `id`/`name`/`enabled`/`priority`(/`browser_data`)
>    5 个字段（`account_manager.py:226-244`）。
>    → 统一网关的账号运行态必须由**网关自己持久化**（§6.6），否则网关重启后丢失全部冷却/失败计数。

#### `chatgpt` 适配器

| 项 | 实现 |
|---|---|

## 5. 请求处理流水线

### 5.1 阶段划分 `[设计]`

```
① 接入    解析入站协议 → 归一化为 NormalizedRequest
② 鉴权    解析 sk-a2a-* → 校验 enabled/未过期 → 得到 KeyContext
③ 授权    渠道白名单 ∩ 模型白名单 → 检查 IP 允许列表
④ 限流    Key 级 RPM + 渠道级并发
⑤ 路由    model → 渠道链（原始 ID 直通 / 别名查路由表）
⑥ 选号    在渠道链上逐跳尝试：选账号 → 取租约
⑦ 转发    Adapter.chat(_stream) → 官方平台/本项目 worker
⑧ 转换    上游响应 → 归一化 → 目标协议序列化
⑨ 计量    记录日志 + 用量 + 账号回填 + 释放租约
⑩ 降级    失败则按错误分类决定：换账号 / 换渠道 / 直接返回
```

### 5.2 鉴权与授权 `[设计]`

```python
@dataclass
class KeyContext:
    key_id: int
    name: str
    channels: set[str] | None      # None = 全部已启用渠道
    models: set[str]               # {"*"} = 全部
    limit_tokens: int
    limit_credits: float
    limit_rpm: int
    ip_allowlist: list[str]
    expires_at: int | None
```

**鉴权顺序**（照 wb2api 已验证的顺序 `[实测·gateway.py:302-379]`）：

```
1. 取 Authorization: Bearer <token>
2. 按 prefix 定位候选（走索引 idx_keys_prefix）
3. 常量时间比对哈希（防时序攻击）
4. enabled == 1 且未过期
5. 全局 IP 规则 → Key 级 IP 白名单
6. RPM 限流
```

**授权**：`channels` 为空数组 = 全部当前已启用且已配置渠道；非空则只允许列出的渠道。
模型白名单在路由解析后校验（因为别名可能映射到多个渠道的模型）。

> **常量时间比对必须用** `secrets.compare_digest` 或 `hmac.compare_digest`，
> 不能写 `==`。源项目里 doubao2api（`unified_server.py:580`）与
> chatgpt2api（`auth_service.py:246`）都做对了，统一层照做。

### 5.3 路由解析 `[设计]`

```python
async def resolve_route(model: str) -> list[Target]:
    # 1. 原始 ID：<channel>/<model> 直通，不查表
    if "/" in model and model.split("/", 1)[0] in ADAPTERS:
        ch, mid = model.split("/", 1)
        return [Target(ch, mid, weight=1)]

    # 2. 别名：查路由表
    rule = await db.get_route(model)
    if not rule or not rule.enabled:
        raise UnknownModel(model)

    targets = await db.get_route_targets(model)      # 已按 position 排序
    if rule.strategy == "priority":
        return targets                                # 顺序即优先级
    if rule.strategy == "weighted":
        return weighted_shuffle(targets)              # 按 weight 加权洗牌
    if rule.strategy == "round_robin":
        return rotate(targets, await counter.next(model))
```

**渠道链的意义**：返回的是一个**有序列表**，第 1 跳失败后自动尝试第 2 跳，
这就是「跨渠道降级」的实现。原始 ID 直通保证了"永远有兜底"。

**模型名前缀的坑** `[实测]`：wb2api 用 `cn:`/`global:` 前缀决定路由池
（`resolve_model.go:13-23`），出站前会**剥离**为裸名。
适配器必须正确处理"入站带前缀 → 出站剥前缀"，否则上游会报模型不存在。
wb2api 的白名单比对逻辑是"去 `cn:` 前缀比对、保留 `global:`"（`keysvc.py:73-83`），
这个不对称规则要在适配器里显式复现。

### 5.4 账号选择与并发 `[设计]`

见 §6.3（选号算法）与 §6.4（并发租约）。

**在渠道链上的选号流程**：

```
for target in targets:                       # 逐跳
    if not channel_enabled(target.channel): continue
    if not key_allows(target.channel, target.model): continue
```

**统一走 OpenAI 形状**（ADR-6）。适配器只需要把 `NormalizedRequest`

### 5.6 流式处理 `[设计]`

**统一用 SSE，逐字节透传 + 旁路扫描**。这是 wb2api 验证过的做法 `[实测·gateway.py:579-615]`：

```python
async def chat_stream(self, req, account):
    async with client.stream("POST", url, json=body, headers=h) as resp:
        async for raw in resp.aiter_bytes():
            yield raw                          # 原样透传，不重新序列化
            self._scan_sse(raw)                # 旁路提取 usage 与首字延迟
```

**为什么要旁路扫描而不是解析后重发**：

- 重新序列化会引入延迟（首字延迟是核心指标）；
- 上游可能发非标准事件，重发会丢信息；
- 但**计费与首字延迟必须拿到** → 用一个不干预流的扫描器旁路提取
  （wb2api 的 `_scan_sse`，`gateway.py:390`）。

**协议转换的流式处理**：Anthropic / Responses 需要真正的转换，
此时不能纯透传。wb2api 的做法是逐行解析 OpenAI SSE 帧再翻成目标事件流
（`anthropic.py:870-981`、`responses.py:1080-1159`），
并且**收尾顺序有要求**：Anthropic 必须先发 `error` 再发 `message_stop`
（`anthropic.py:948-969`）。

### 5.7 错误分类与重试/降级 `[设计]`

**先分类，再决策**。照 wb2api 的 `Classify`（`client.go:1037`）设计统一错误枚举：

| 错误类型 | 触发 | 处理动作 |
|---|---|---|
| `hard_credit` | 余额耗尽（402） | 账号冷却到次日；换号 |
| `soft_rate` | 限流（429） | 账号软冷却；换号 |
| `model_limited` | 模型级限流（6004） | **模型级**冷却；换模型或换渠道 |
| `model_not_found` | 无此模型（11102） | 模型负缓存 6h；换渠道 |
| `waf_block` | WAF 拦截（403） | 账号冷却；多账号同时 403 → **终止轮转**（IP 级问题） |
| `session_dead` | 会话失效 | 刷新凭据；连续 3 次 → 禁用 |
| `not_found` | 上游 404 | 短冷却 60s |
| `bad_params` | 参数错误 | **不重试**，直接返回（重试也是错） |
| `content_blocked` | 内容拦截 | 触发提示词降级重试一次 |
| `server_error` | 上游 5xx | 换号重试 |

**关键判据**：

- `bad_params` **绝不能重试**——参数错误重试 N 次只是浪费 N 倍时间，且会污染账号健康度。
- `waf_block` 要检测**跨账号相关性**：短窗口内多个账号都被 403，
  说明是**出口 IP 被拦**而非账号问题，此时继续轮转毫无意义（wb2api 的 `wafip.go` 实现了这个）。

**退避**：轮转间退避 `500ms × 2^i`，封顶 8s，±25% 抖动（wb2api `backoffAfter`）。

## 6. 账号池与调度引擎

### 6.1 池结构 `[设计]`

```python
class AccountPool:
    _by_id: dict[str, AccountRuntime]      # 全局 id → 运行态
    _by_channel: dict[str, list[str]]      # 渠道 → 账号 id 列表
    _leases: dict[str, int]                # 账号 id → 在途计数
    _lock: asyncio.Lock                    # 串行化状态迁移

class AccountRuntime:
    """运行态：高频读写，不落库。"""
    id: str
    channel: str
    credits: float
    credits_expiring: float
    cooldown_until: float
    breaker_until: float
    degrade_until: float
    model_cooldowns: dict[str, float]      # 模型级冷却
    consecutive_fails: int
    soft_streak: int
    success_count: int
    err_total: int
    inflight: int
```

**为什么要 `_lock`**：源项目验证过必要性——doubao2api 的
`AccountManager` 用 `asyncio.Lock` 串行化全部状态变更（`account_manager.py:170`），
否则并发请求会读到不一致的计数。

### 6.2 冷却 / 熔断 / 降权参数 `[实测来源 + 设计统一]`

参数直接采用 wb2api 的实测默认值（它的策略最完善）：

| 机制 | 触发 | 时长 | 字段 |
|---|---|---|---|
| 硬冷却 `CoolHard` | 余额耗尽（402） | 到**次日 04:00** | `cooldown_until` |
| 软冷却 `CoolSoft` | 限流（429） | 有上游重置时间则对齐；否则 600s 起指数退避，封顶 **2h** | `cooldown_until`, `soft_streak` |
| 模型级冷却 | 模型限流（6004） | `min(上游resetAt, now + 2h)` | `model_cooldowns[model]` |
| 模型负缓存 | 无此模型（11102） | 6h 起指数退避，封顶 24h | `model_cooldowns[model]` |
| 404 短冷却 | 上游 404 | 固定 **60s** | `cooldown_until` |
| WAF 冷却 | WAF 403 | 60s 起（带抖动）指数退避，封顶 2h | `cooldown_until` |
| **熔断** | 连续失败达 **3** 次 | 30m 起指数退避，封顶 **6h** | `breaker_until` |
| **连败降权** | 连续失败达 **5** 次 | 固定 **10m**（钳到 2h 上限） | `degrade_until` |
| 会话失效 | 会话死 | 连续 **3** 次 → 禁用 | `session_dead_fails` |

**恢复规则**：成功后清空 `fails`/`breaker_until`/`soft_streak`/`consecutive_fails`/`degrade_until`
（wb2api `state.go:246-261` 的实现）。
但**签到解冻只清冷却域、不清熔断**（`state.go:119-130`）——
这个区别很重要：额度恢复了不等于账号健康了。

当前过渡实现将渠道/模型运行态持久化到 SQLite `channel_runtime_state`，并对 WorkBuddy 做有限账号结果记录。目标态由统一 scheduler 管理三渠道账号租约、冷却和熔断；adapter 必须返回可信的账号引用，否则只记录渠道级结果，不伪造账号归因。不得依赖源项目追踪头、源项目账号快照或“上游自行选号”的兼容行为。

### 6.3 选号算法 `[设计]`

采用「**评分 → 短名单 → 加权随机 → 兜底**」四段式，融合三家的优点：

```python
async def pick(channel: str, model: str) -> AccountRuntime | None:
    # ① 硬过滤
    cands = [a for a in by_channel(channel)
             if a.enabled
             and not a.system_disabled
             and not a.manual_disabled
             and a.healthy_for_model(model)      # 全账号健康 且 该模型不在冷却
             and a.inflight < a.max_concurrent]

    if not cands:
        return pick_cooling_fallback(channel, model)   # ④ 兜底

    # ② 评分
    scored = sorted(cands, key=lambda a: -score(a), )
    shortlist = scored[:5]                             # Top5 短名单

    # ③ 加权随机（避免热点账号被打爆）
    return weighted_choice(shortlist, weight=score)


def score(a) -> float:
    """跨渠道一致的评分因子。"""
    return (
        a.credit_ratio()      * 10      # 额度余量
      + a.expiring_ratio()    * 8       # 快过期额度占比（优先消耗）
      + a.recent_success_rate() * 6     # 近期成功率
      + a.idle_weight()                 # 空闲权重（在途越少越高）
      - a.degrade_penalty()             # 降权惩罚
    )
```

**兜底逻辑**（`pick_cooling_fallback`）：从"非禁用、非硬冷却"的账号里选
**冷却截止最早**的那个。理由：全冷却时，与其直接返回 503，
不如赌一把最早恢复的账号——它可能已经恢复了只是状态没刷新
（wb2api `pick.go:232-270` 的做法）。

**成本分层** `[设计·可选]`：wb2api 按实测扣费把模型分 tier 0/1/2，
优先用最优层；某层垄断时条件探索其他层（`pick.go:96-146`）。
这是成本优化，建议**二期再做**——它依赖足够的实测数据积累。

### 6.4 并发与租约 `[设计]`

```python
async def acquire(account_id: str) -> Lease:
    async with self._lock:
        rt = self._by_id[account_id]
        if rt.inflight >= rt.max_concurrent:
            raise NoCapacity
        rt.inflight += 1
        return Lease(account_id, ts=now())

async def release(lease: Lease, success: bool, kind: ErrKind | None = None):
    async with self._lock:
        rt = self._by_id[lease.account_id]
        rt.inflight -= 1
        if success:
            note_success(rt)
        else:
            note_failure(rt, kind)
```

**并发上限的来源差异** `[实测]`：

| 渠道 | 上限 | 来源 |
|---|---|---|
| wb | 按 realm 分档 | Go 侧 `Acquire` 内部 |
| doubao | `max_concurrent`（默认 1） | `account_manager.py:130-134` |
| chatgpt | `image_account_concurrency`（默认 3，仅图片） | `config.py:418-423` |

→ provision 流程把渠道并发上限写进账号的 `ext.max_concurrent`，
网关的 `AccountRuntime.max_concurrent` 用它初始化。

**防撞号** `[设计]`：同一账号在 100ms 内被连续选中时，应重新抽签
（wb2api `pick.go` 里有这个保护）。理由：并发请求几乎同时进来时，
Top5 短名单会高度重叠，不加保护容易把同一个账号压满。

### 6.5 会话粘性 `[设计]`

**默认关闭**，但提供配置。理由 `[实测]`：

- doubao2api **完全没有**会话粘性——同一个 `conversation_id` 的连续请求
  可能落到不同账号（`unified_server.py:980` 每次独立选号），
  多轮上下文靠上游 `conversation_id` 维持；
- wb2api **有**会话粘性（`gateway/internal/session/`），支持 Redis 存储。

统一层设计为可配置：

```python
class StickyPolicy(str, Enum):
    OFF = "off"          # 不粘（默认，最大化负载均衡）
    SESSION = "session"  # 同 conversation_id 粘同一账号
    KEY = "key"          # 同 API Key 粘同一账号
```

粘性开启时的收益：上游侧会话复用（减少重复建连、提高缓存命中）。
代价：负载不均，且粘住的账号冷却时需要重新分配。

### 6.6 状态持久化 `[设计]`

**必须 All2API 自己持久化运行态**（平台 adapter 或 worker 重启不应丢失统一调度事实）：

当前已落地的子集是 WorkBuddy 过渡运行态，使用 SQLite `account_runtime_state` 与账号快照分离。全渠道选号、租约和可信账号回报仍是迁移任务；以下 `state.json` 仅为目标格式示例，不表示当前已实现。

```json
// data/gateway/state.json
{
  "version": 1,
  "saved_at": 1758780000,
  "accounts": {
    "wb:workbuddy-5a1e3ce9": {
      "credits": 1234.5,
      "credits_expiring": 200.0,
      "cooldown_until": 0,
      "breaker_until": 1758783600,
      "degrade_until": 0,
      "model_cooldowns": {"glm-5.2": 1758781800},
      "consecutive_fails": 2,
      "soft_streak": 0,
      "success_count": 412,
```

**落盘策略**：原子写（tmp + rename，0600 权限），每 10s 或有变更时落盘。
行为上参考源项目的原子落盘实现，但目标代码必须使用本项目的 CredentialStore/Repository，
不能读取或写回源项目文件。

**择新恢复** `[设计]`：启动时比较本地运行态与 adapter/平台客户端返回的状态，

## 7. 数据存储设计

### 7.1 选型 `[设计]`

| 数据 | 存储 | 理由 |
|---|---|---|
| 渠道/账号/模型/路由/密钥 | **SQLite** `all2api.db` | 需要事务与查询；数据量小（百级） |
| 请求日志 | **SQLite** + 定期归档 | 需要按维度查询（渠道/密钥/模型/状态） |
| 用量日聚合 | **SQLite** | 预聚合，避免每次查询扫全表 |
| 账号运行态 | SQLite `account_runtime_state`（当前可信账号结果） | 与本地 provision 账号快照隔离，事务写入且重启后可读；完整调度器状态仍待设计契约落地 |
| 密钥明文 | **不存**，只存哈希 | 安全 |
| 会话 | **内存**（可选落盘） | 重启失效可接受；管理会话本就该短命 |

**WAL 模式必须开** `[实测]`：wb2api 用 `PRAGMA journal_mode=WAL` +
`synchronous=NORMAL`（`db.py:315-318`），在"读多写多"的日志场景下显著减少锁竞争。

### 7.3 迁移机制 `[设计]`

照 wb2api 的自研方案（`db.py:339-389`），不引入 Alembic：

```python
_MIGRATIONS = (
    # (表, 列, 列定义)
    ("request_logs", "fallback_depth", "INTEGER NOT NULL DEFAULT 0"),
    ("request_logs", "route_alias",    "TEXT"),
    ("accounts",     "quota_unit",     "TEXT NOT NULL DEFAULT 'none'"),
    ...
)

def _migrate(conn):
    for table, col, decl in _MIGRATIONS:
        cols = {r["name"] for r in conn.execute(f"PRAGMA table_info({table})")}
        if col not in cols:
            conn.execute(f"ALTER TABLE {table} ADD COLUMN {col} {decl}")
```

**主键变更需要重建表** `[实测]`：SQLite 不支持 `ALTER` 主键。
wb2api 为此写了 `_rebuild_usage_daily_pk`（`db.py:392-482`）——
新建表 → 拷数据 → 删旧表 → 改名。统一层若遇到同类需求照做。

### 7.4 状态分层 `[设计]`

必须明确区分**两类状态**，这是源项目踩过的坑：

| 类别 | 例子 | 存储 | 重启后 |
|---|---|---|---|
| **配置态** | 渠道配置、密钥、路由规则、账号启用开关 | SQLite | 保留 |
| **运行态** | 冷却截止、连续失败、在途计数、额度余量 | `state.json` + 内存 | **需要择新恢复**（§6.6） |
| **派生态** | 统一状态（8 态）、成功率、可用账号数 | 不存 | 实时计算 |

> **不要持久化派生态** `[设计]`：状态是由多个维度算出来的
> （`status_override` → 凭据 → 过期 → 禁用 → 冷却 → 模型冷却 → 在途 → ready）。
> 存下来必然与维度不同步。源项目都是运行时派生，统一层照做。

### 8.3 错误码规范 `[设计]`

统一为 OpenAI 错误体，**并附上可操作建议**：

```json
{
  "error": {
    "type": "channel_unavailable",
    "code": "all_accounts_cooling",
    "message": "渠道 wb 的全部账号都在冷却中，最早 3 分 20 秒后恢复",
    "advice": "检查账号池健康度，或为路由规则添加备用渠道",
    "channel": "wb",
    "retry_after": 200
  }
}
```

**`advice` 字段是统一层新增的** `[设计]`：源项目的错误只给原因不给动作
避免失败详情只出现在瞬时 toast 或被静默吞掉；管理面响应要保留可追踪的错误码与 request ID。
网关作为统一入口，有能力给出跨渠道的处理建议。

**HTTP 状态码映射**：

| 状态码 | 场景 |
|---|---|
| 400 | 参数错误（`bad_params`，**不重试**） |
| 401 | 密钥无效/过期 |
| 403 | IP 不在白名单 / 渠道或模型未授权 |
| 404 | 模型不存在 / 无渠道支持该能力 |
| 429 | 密钥 RPM 超限 / 全部账号限流（带 `Retry-After`） |
| 503 | 全部渠道不可用 |
| 504 | 上游超时 |

## 9. 管理面 API 设计

### 9.1 认证 `[设计]`

| 方式 | 用途 | 校验 |
|---|---|---|
| Session Cookie（HttpOnly, SameSite=Lax） | 浏览器控制台 | HMAC 签名，载荷含 `username`/`role`/`sv`/`exp` |
| 管理令牌 `wbt_` | 脚本/CI | 按 prefix 定位 + 常量时间比哈希 |
| **不允许**数据面密钥访问管理面 | — | 反之亦然 |

照 wb2api 已验证的实现（`security.py:152-196` 签名 Cookie，
`tokensvc.py:116-127` 令牌校验），另外加上它做对的几件事：

- **会话版本 `sv`**：改密/强制下线时递增，旧 Cookie 立即失效（`security.py:362-385`）
- **登录防爆破**：按 IP + 按用户名双计数，5 次/600s 锁定（`security.py:318-346`）
- **CSRF**：非 GET 请求校验 `Origin` host == `Host`
  （doubao2api `unified_server.py:585-590` 的做法）
- **审计**：所有写操作落 `audit_logs`

### 9.3 与迁移来源的关系 `[设计]`

网关的管理面**不暴露三个源项目的管理接口**。目标管理面通过 registry 调用本项目
内置 adapter/provisioner，并聚合为统一 DTO：

| 统一端点 | 聚合来源 |
|---|---|
| `GET /admin/api/accounts` | 本地 `accounts` 表中的 provision 结果和网关运行态 |
| `GET /admin/api/overview` | 内置渠道健康 + 网关自己的日志聚合 |
| `GET /admin/api/stats/*` | **网关自己的 `usage_daily`**（上游没有跨渠道维度） |
| `GET /admin/api/logs` | **网关自己的 `request_logs`** |

**为什么统计和日志必须网关自己算** `[设计 + 迁移事实]`：

- wb2api 的日志**没有渠道维度**（它只有 `realm`），且账号回填链路是坏的；
- doubao2api 的日志是**内存 100 条环形缓冲**（`unified_server.py:229`），重启即丢，
  而且 `/auth`、`/admin`、`/health` 路径**不记录**（`_UNLOGGED_PREFIXES`，`:838`）；
- chatgpt2api 只有操作日志，**没有请求级日志**。

所以统一层的日志与统计**只能自己产出**，迁移来源的旧日志格式只作为行为参考，
不作为目标运行数据源。

## 10. 横向扩展：新增平台的实现契约

### 10.1 三步法 `[设计]`

```
第 1 步 · 创建 adapter 包  第 2 步 · manifest/config      第 3 步 · contract/注册
┌──────────────────┐      渠道名称 / slug               账号选择策略
│ WorkBuddy  adapter│      内置 client/worker 配置       fake 上游 fixture
│ Doubao    adapter│      capability + flow schema      错误映射矩阵
│ ChatGPT   adapter│      Secret 引用/资源限制           registry 注册
│ NewPlatform       │  ← 只增加代码包，不改通用核心
└──────────────────┘
```

### 10.2 适配器实现清单 `[设计]`

新增一个平台需要交付的东西（**这是一份 checklist，不是描述**）：

| # | 交付项 | 说明 |
|---|---|---|
| 1 | `adapters/<name>/manifest.py` | slug、能力、协议、配置 schema、账号 flow 和版本 |
| 2 | `adapters/<name>/adapter.py` | `health` / `list_models` / `invoke` / `invoke_stream` / `map_error`；不写 Key 授权 |
| 3 | `adapters/<name>/provisioner.py` | `describe` / `start` / `poll` / `complete` / `import` / `cancel` / `refresh` |
| 4 | `adapters/<name>/schemas.py` + `mapper.py` | canonical Account/Model/Usage 与 `ext` 版本映射 |
| 5 | `adapters/<name>/errors.py` | 平台错误 → 统一 `ErrorKind`、重试和冷却策略 |
| 6 | `adapters/<name>/tests/contract/` | mock/fake 平台、账号状态机、Secret 脱敏和协议契约 |
| 7 | 配置/许可证/注册 | manifest registry、配置迁移、依赖许可证和来源矩阵 |

**总共 7 项，其中 6 项都在 `adapters/<name>/` 目录内。**
网关核心、数据库、管理 API、前端页面**都不需要改**——这是 ADR-2 的验收标准。

### 10.3 不改动的部分（可扩展性的证明）`[设计]`

注册后**自动生效**的位置：

- 渠道列表页（读适配器注册表渲染卡片）
- 账号池页的渠道筛选器（读已注册渠道）
- 日志页的渠道筛选下拉
- 统计页的渠道维度
- 模型路由的目标选择器
- 调试台的渠道下拉
- 接入向导的第 1 步列表

### 11.1 拓扑 `[设计]`

```
                    ┌──────────────────────────────────────┐
   公网/内网 ────────►│  all2api-gateway  :8080              │
                    │  单容器 · 2 CPU / 2GB 起              │
                    │  data/all2api.db + data/gateway/      │
                     └───┬──────────┬──────────┬────────────┘
                         │          │          │
          ┌──────────────┘          │          └──────────────┐
          ▼                         ▼                         ▼
 ┌─────────────────┐   ┌──────────────────────┐   ┌──────────────────┐
 │ workbuddy       │   │ doubao               │   │ chatgpt          │
 │ adapter/worker  │   │ adapter + Chromium  │   │ adapter/client   │
 │ 本仓库代码       │   │ 本仓库代码           │   │ 本仓库代码       │
 └─────────────────┘   └──────────────────────┘   └──────────────────┘
```

**资源估算依据** `[实测]`：
doubao2api 每账号一个 Chromium persistent context，
`max_concurrent=1` 时每个活跃账号约需 300-500MB 内存。
**N 个账号同时启用时内存需求是 N×400MB 量级**，这是最大的资源约束。

### 11.2 关键配置 `[设计]`

目标配置只描述本项目内置 client/worker、官方平台地址、OAuth client、浏览器资源、
加密存储和并发限制。旧 `A2A_*_UPSTREAM_BASE`/外部管理令牌只能出现在迁移期
`legacy_bridge` profile，默认关闭，不得进入生产必填配置。

```yaml
# config.yaml
server:
  host: 0.0.0.0
  port: 8080
  base_path: ""              # 反代部署前缀

storage:
  db: ./data/all2api.db
  state: ./data/gateway/state.json

security:
  session_days: 1            # 会话总寿命
  session_idle_hours: 12     # 空闲上限
  secure_cookie: auto        # auto / true / false
  trust_proxy: true          # 是否信任 X-Forwarded-*
  trusted_proxy_hops: 1
  trusted_proxies: [127.0.0.1, ::1] # A2A_TRUSTED_PROXIES；仅可信 IP/CIDR 才读取转发头
  login_max_fails: 5         # 5 次 / 600s 锁定

scheduler:
  pick_top_n: 5              # 短名单大小
  breaker_threshold: 3       # 熔断阈值
  breaker_cooldown: 30m
  breaker_cooldown_max: 6h
  degrade_threshold: 5       # 降权阈值
  degrade_cooldown: 10m
  soft_cooldown: 600s        # 软冷却基数
  soft_cooldown_max: 2h
  retry_max_hops: 3          # 跨渠道最大跳数
  retry_backoff_base: 500ms
  sticky: off                # off / session / key

channels:
  - slug: wb
    adapter: wb
    client:
      platform_base: ${WB_PLATFORM_BASE}
      realm: cn
    credential_store: encrypted
    enabled: true
  - slug: doubao
    adapter: doubao
    browser:
      executable: ${DOUBAO_BROWSER_EXECUTABLE}
      profile_root: ./data/browser/doubao
    credential_store: encrypted
    enabled: true
  - slug: chatgpt
    adapter: chatgpt
    client:
      platform_base: ${CHATGPT_PLATFORM_BASE}

  usage_retention_days: 365  # 用量聚合保留
```

> **日志保留必须配清理** `[设计]`：源项目都没做，导致
> `request_logs` 会无限增长。当前网关提供 admin-only `POST /admin/api/logs/clear`，
> 按 `retention_days` / `usage_retention_days` 在一个事务内删除旧明细和旧聚合；
> 请求写入时已完成 `usage_daily` 聚合，因此清理不会从明细回填。外部 cron 可按需调用，
> 多 worker 下暂不在 lifespan 中自动启动重复清理任务。

### 11.3 可观测性 `[设计]`

| 维度 | 实现 |
|---|---|
| 健康检查 | `GET /admin/api/healthz` — 返回网关 + 各渠道 + 存储的状态 |
| 指标 | `GET /admin/api/metrics` — 请求数/延迟分布/错误率/账号可用数 |
| 渠道健康 | 每 30s 调用各内置 adapter 的 `health()`，失败区分配置/凭据/平台/worker 并标记 `degraded` |
| 审计 | 所有写操作落 `audit_logs`（actor/action/target/detail/ip） |
| 日志 | 结构化 JSON 输出到 stdout，容器日志驱动收集 |

**探测路径必须加入请求日志跳过列表** `[设计约束]`：
健康探测会周期运行，不应污染用户请求日志或用量统计；探测路由必须有固定识别规则并在日志/计量中排除。

### 11.4 安全 `[设计]`

| 项 | 做法 |
|---|---|
| 密钥存储 | 只存 `sha256` 哈希；明文仅在创建时返回一次 |
| 凭据保护 | 账号凭据（token/OAuth/Cookie/profile）由本项目加密 CredentialStore/受控 worker 管理，不回传客户端 |
| Cookie | `HttpOnly` + `SameSite=Lax` + 可选 `Secure`；HMAC 签名 |
| CSRF | 非 GET 校验 `Origin` |
| 防爆破 | IP + 用户名双计数锁定 |
| 时序攻击 | 密钥比对用 `compare_digest` |
| 权限隔离 | 数据面密钥 ≠ 管理面令牌；`admin`/`viewer` 两档角色 |
| 文件权限 | DB 与状态文件 `chmod 0600`（含 `-wal`/`-shm`） |
| 出站代理 | 由对应内置 adapter 的 client 配置，Secret 和代理凭据走安全注入 |

## 13. 风险与已知问题

### 13.1 源项目实测缺陷（融合时必须处理）

这些是审计中**真实发现**的问题，不是假设。统一层若不处理，会把缺陷继承过来：

| # | 缺陷 | 证据 | 统一层处理 |
|---|---|---|---|
| 1 | **账号回填链路是坏的** | `accountlog.py:118` 调用 `db.attach_request_accounts()`，该函数**全仓无定义**；`request_logs` 无 `account` 列。异常被 `except` 吞掉只记 warning（`accountlog.py:121-132`） | 网关自己实现回填（§5.8）——转发前就知道用了哪个账号 |
| 2 | **"全部测活"只测一个账号** | `POST /admin/api/probe` 不读任何参数，直接 `_acquire_account()`（`unified_server.py:2480-2496`） | `probe(cfg, native_ids: list[str])` 强制批量语义（§4.2） |
| 3 | **豆包二维码根本不显示** | 前端读 `result.qr_image`，后端返回 `qr_image_base64`（`unified_server.py:2691`） | 统一 `LoginFlow.qr_image_base64` 为唯一字段名（§4.2） |
| 4 | **`priority` 字段不参与调度** | `_select_account()` 排序 key 无 `priority`（`account_manager.py:295-299`） | 网关自己做评分选号（§6.3）；`priority` 作为评分因子之一真正生效 |
| 5 | **doubao 账号运行态不落盘** | `meta.json` 只存 5 个字段（`account_manager.py:226-244`）；冷却/失败计数重启即丢 | 网关自己持久化（§6.6），并做择新恢复 |
| 6 | **`temperature` 声明但不生效** | 全仓仅 `unified_server.py:272` 一处声明，无消费点 | 适配器能力声明标注**实际生效**的参数，界面禁用无效控件（§5.5） |
| 7 | **doubao 日志是内存 100 条** | `deque(maxlen=100)`（`unified_server.py:229`）；`/auth`、`/admin`、`/health` 不记（`:838`） | 网关自己产出请求日志（§9.3） |
| 8 | **两套失败计数不同步** | 客户端级阈值 5（`browser_client.py:126`）与账号池级阈值 3（`account_manager.py:135`）独立计数 | 网关统一一套计数（§6.2） |
| 9 | **会话粘性缺失** | doubao 每次请求独立选号（`unified_server.py:980`），同 `conversation_id` 可能换账号 | 可配置的粘性策略（§6.5），默认关闭 |
| 10 | **三个 error 字段语义不同** | chatgpt2api 的 `last_refresh_error`（access_token 失效）vs `last_token_refresh_error`（refresh_token 失败） | 分别映射到 `last_error` 与 `ext.last_token_refresh_error`（§4.4） |
| 11 | **wb2api 三套凭据易混用** | `wbk_`（数据面）/ `wbt_`（管理面）/ Go 入站 `api_key` | 对外只暴露一套；管理令牌不得用于数据面（ADR-8） |

### 13.2 设计风险 `[风险]`

| 风险 | 影响 | 缓解 |
|---|---|---|
| **上游接口随时会变** | 适配器失效，渠道不可用 | 适配器隔离 + 渠道级降级；契约测试覆盖 |
| **doubao 的内存需求随账号数线性增长** | N 个账号 = N×400MB | 限制同时启用的账号数；按需启用（`enabled=false` 启动时跳过，已验证 `account_manager.py:450-452`） |
| **高频轮询管理接口可能被上游限流** | 状态刷新失败 | 分级轮询：活跃账号 30s、冷却账号 5min、禁用账号不轮询 |
| **调度延迟** | 每次请求要选号 + 可能轮转，P95 延迟上升 | 选号在内存完成（无 IO）；轮转退避有上限（封顶 8s） |
| **跨渠道降级的语义风险** | 不同渠道的模型能力不同，降级后输出质量可能骤降 | 降级只在同 `kind` 内发生；日志记 `fallback_depth` 供事后审计 |
| **`ext{}` 无索引** | 无法按渠道特有字段查询 | 可接受（§7.2）；若确有需求再提升为独立列 |
