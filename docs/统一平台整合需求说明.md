# All2API 统一平台整合需求说明

> 文档类型：产品与技术联合基线  
> 状态：开发必须遵循  
> 适用范围：All2API 后端、管理前端、适配器、部署和测试

## 1. 要解决的问题

WorkBuddy、Doubao、ChatGPT 原本分散在三个项目中（后续加入 Grok），账号、模型、协议和调用入口各自独立，维护和部署成本高。All2API 把这些渠道的能力收敛到一个代码仓库、一个管理面和一个对外网关中。

参考项目只用于一次性代码审计、行为提取、协议 fixture 和迁移验证。它们不能成为 All2API 的运行时、构建时或数据依赖：不能 import、不能请求其端口、不能读取其数据库/账号目录、不能启动其进程，也不能把它们作为 Git submodule。

“融合”指把新增账号、凭据生命周期、模型发现、协议调用和账号池能力重写/迁移到本仓库的渠道适配器中。允许浏览器 worker 或平台 worker 独立进程，但 worker 的源码、镜像、配置、健康检查和测试必须由 All2API 管理。

## 2. 必须交付的能力

| 编号 | 要求 | 完成证据 |
|---|---|---|
| REQ-01 | 在同一个管理面分别管理 `wb`、`doubao`、`chatgpt`、`grok` 的渠道、模型、账号和状态 | `/admin/api/channels`、`/models`、`/accounts` 可按渠道筛选，所有渠道使用同一套页面/API |
| REQ-02 | 对外只提供一个 Base URL 和 All2API Key；调用方用 `<channel>/<model>` 指定渠道 | 同一 `/v1` 地址分别完成各渠道调用，未授权渠道返回 403 |
| REQ-03 | 创建/编辑 Key 时可以选择一个或多个渠道，并可限制模型 | Key 持久化 `channels/models` scope，alias 展开后仍执行授权检查 |
| REQ-04 | 新增账号第一步必须选渠道，第二步才展示该渠道的 flow 和动态字段 | 未选渠道不能提交；切换渠道会清理旧表单和 session；三渠道流程均有成功、失败、取消、过期测试 |
| REQ-05 | 后续新增平台通过代码扩展，不在页面执行任意代码 | 只新增 `internal/adapters/<slug>/`、配置、registry 注册和契约测试，通用 handler、数据库表和页面无需平台分支 |
| REQ-06 | 遵守企业级工程规范 | 分层目录、锁定依赖、迁移、审计、日志脱敏、CI、许可证和隔离构建门禁全部通过 |

## 3. 目标架构

```text
外部客户端
    │  https://gateway.example/v1 + sk-a2a-...
    ▼
All2API
├─ web/                         管理控制台
├─ cmd/all2api/                 Go 主服务入口和依赖装配
├─ cmd/doubao-browser-worker/   浏览器 worker（独立进程）
├─ cmd/media-worker/            媒体 worker（独立进程）
└─ internal/
   ├─ domain/                   Key scope 等纯领域规则
   ├─ application/              用例、事务、审计和授权编排
   ├─ ports/                    Adapter/Provisioner/Repository 接口
   ├─ adapters/<slug>/          平台私有协议、账号流程和映射
   ├─ infrastructure/           SQLite、加密、媒体、Token 估算、安全
   └─ transport/http/           认证、管理面和统一数据面
```

依赖方向固定为 `transport/http → application → domain`，`adapters/infrastructure` 实现 `ports`。`domain` 不得依赖 HTTP、SQLite、浏览器或任何源项目包；handler 和 Web 不得写 `if channel == ...` 形式的平台业务分支。

核心对象：

- `ChannelManifest`：稳定 slug、显示名、版本、协议、能力、配置 schema、账号 flow 和健康状态。
- `Account`：统一状态、渠道、脱敏 native id、配额、运行态和 `credential_ref`；平台字段只进版本化 `ext`。
- `GatewayKey`：哈希后的 Key、过期时间、RPM、`allowed_channels`、`allowed_models`。
- `UpstreamAdapter`：模型发现、调用、流式响应、错误映射和健康检查。
- `AccountProvisioner`：账号新增、主动导入、轮询、完成、取消、按渠道支持的刷新和删除；不提供外部账号同步。Cookie/browser 渠道没有 token refresh endpoint 时必须显式返回 `capability_not_supported`，不能伪造刷新成功。

## 4. 对外调用和授权

默认 Base URL 为 `http://localhost:8888`，生产使用 HTTPS；数据面路径为 `/v1`。调用方只需要一把 All2API Key：

```bash
curl "${ALL2API_BASE:-http://localhost:8888}/v1/chat/completions" \
  -H "Authorization: Bearer $ALL2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"wb/cn:glm-5.2","messages":[{"role":"user","content":"hello"}]}'

curl "${ALL2API_BASE:-http://localhost:8888}/v1/chat/completions" \
  -H "Authorization: Bearer $ALL2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"doubao/doubao-pro","messages":[{"role":"user","content":"hello"}]}'

curl "${ALL2API_BASE:-http://localhost:8888}/v1/chat/completions" \
  -H "Authorization: Bearer $ALL2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"chatgpt/gpt-4o-mini","messages":[{"role":"user","content":"hello"}]}'
```

Key 创建示例：

```http
POST /admin/api/keys
```

```json
{
  "name": "team-a",
  "channels": ["wb", "chatgpt"],
  "models": ["wb/*", "chatgpt/gpt-4o-mini"],
  "limit_rpm": 60,
  "expires_at": null
}
```

`channels=[]` 代表全部当前已启用且已配置渠道；Key 明文只在创建或轮换响应中返回一次。请求流程必须先解析 Key，再校验渠道和模型 scope，最后才允许 scheduler 选择账号。别名展开后对每个实际目标再次校验，不能借此绕过授权。

## 5. 新增账号：先选渠道，再执行渠道方法

统一流程如下：

```text
选择 channel
  → 读取该 channel 的 provision-schema
  → 选择 flow 并提交动态 payload
  → start / poll / complete 或 import / cancel
  → CredentialStore 加密保存
  → 归一化 Account、审计、刷新模型目录
```

这里的 `import` 是管理员主动提交本次新增账号的凭据材料；账号目录不会从三个源项目或其他外部
服务同步。旧的 `/admin/api/accounts/sync` 已删除，账号列表只来自本项目的 provision 结果。

第一步只能选择已注册渠道；未选择渠道时不展示平台字段。通用账号服务只负责校验 channel/flow/schema、幂等、TTL、审计和持久化，不认识 `realm`、`account_id`、`callback`、`access_token` 等平台字段。

各渠道的新增账号能力已在本仓库用 Go 重写，flow 和实现位置见[账号新增流程](账号新增流程.md)第 4、7 节；来源项目的方法映射和许可证记录见 [`archive/python-era/三渠道代码迁移矩阵.md`](archive/python-era/三渠道代码迁移矩阵.md)。不允许通过 import、HTTP、文件共享或进程调用把源项目包装成依赖；今后迁移外部行为时，必须登记源版本、文件/符号、许可证、改写范围、fixture、测试和负责人。

## 6. 新平台扩展位置

新增平台在 `internal/adapters/<slug>/` 下实现 `ports.Adapter`（模型目录、调用、流式、错误映射）和可选的 provisioner，目录模板和步骤见[渠道适配器开发规范](渠道适配器开发规范.md)。

然后在 `internal/adapters/registry/registry.go` 注册 manifest、在 `cmd/all2api/main.go` 装配、补充 `.env.example` 配置、数据库迁移（如确有必要）、告警和文档。禁止在通用 handler、application、数据库表或前端组件新增平台专用分支；如果确需修改核心，必须证明它是所有渠道共有的 port/领域规则并提交 ADR。

## 7. 当前状态

Go 是唯一后端运行时，Python 后端和 legacy bridge 已删除。四渠道 native adapter/provisioner、二维码会话、加密凭据和本地账号目录已实现。

真实平台 E2E 通过前不得声明渠道已验收。每个渠道必须同时完成：内置 client/worker、账号新增与刷新、模型和调用、Key scope、契约/集成/E2E 测试、安全扫描、API/配置/运维文档，以及 `verify-go-clean-build.ps1` 隔离构建运行。

## 8. 开发顺序和完成定义

1. **M0 基线**：冻结契约、审计来源、许可证和脱敏 fixture。（完成）
2. **M1 内核**：domain/ports、registry、Key 授权、账号状态机和 fake adapter。（完成）
3. **M2-M4 渠道内置**：WorkBuddy、Doubao、ChatGPT、Grok 的 provisioner、凭据、client/worker 和协议。（本地完成，真实平台 E2E 待验收）
4. **M5 切换**：Go 成为唯一运行时，删除 Python 和 bridge。（完成）
5. **M6 扩展与发布**：fake/new adapter 证明通用 API、页面和数据库不需平台分支；CI 与发布门禁。

完成定义：`gofmt`/`go vet`/`go test`、前端 lint/typecheck/build、供应链和许可证检查通过；隔离环境中能构建、测试、启动；所有渠道均能通过同一 URL + Key 调用；账号新增先选渠道；未授权渠道稳定返回 403；日志、数据库、前端 bundle 和镜像无明文凭据与源路径。
