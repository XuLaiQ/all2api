# All2API 统一平台整合需求说明

> 文档类型：产品与技术联合基线  
> 状态：开发必须遵循  
> 适用范围：All2API 后端、管理前端、适配器、部署和测试

## 1. 要解决的问题

当前 WorkBuddy、Doubao、ChatGPT 分散在三个项目中，账号、模型、协议和调用入口各自独立，维护和部署成本高。All2API 的目标是把三类渠道的**可迁移代码能力**收敛到一个代码仓库、一个管理面和一个对外网关中。

三个现有项目只用于一次性代码审计、行为提取、协议 fixture 和迁移验证。它们不能成为 All2API 的运行时、构建时或数据依赖：不能 import、不能请求其端口、不能读取其数据库/账号目录、不能启动其进程，也不能把它们作为 Git submodule。

“融合”指把新增账号、凭据生命周期、模型发现、协议调用和账号池能力重写/迁移到本仓库的渠道适配器中。允许浏览器 worker 或平台 worker 独立进程，但 worker 的源码、镜像、配置、健康检查和测试必须由 All2API 管理。

## 2. 必须交付的能力

| 编号 | 要求 | 完成证据 |
|---|---|---|
| REQ-01 | 在同一个管理面分别管理 `wb`、`doubao`、`chatgpt` 的渠道、模型、账号和状态 | `/admin/api/channels`、`/models`、`/accounts` 可按渠道筛选，三渠道使用同一套页面/API |
| REQ-02 | 对外只提供一个 Base URL 和 All2API Key；调用方用 `<channel>/<model>` 指定渠道 | 同一 `/v1` 地址分别完成三渠道调用，未授权渠道返回 403 |
| REQ-03 | 创建/编辑 Key 时可以选择一个或多个渠道，并可限制模型 | Key 持久化 `channels/models` scope，alias 展开后仍执行授权检查 |
| REQ-04 | 新增账号第一步必须选渠道，第二步才展示该渠道的 flow 和动态字段 | 未选渠道不能提交；切换渠道会清理旧表单和 session；三渠道流程均有成功、失败、取消、过期测试 |
| REQ-05 | 后续新增平台通过代码扩展，不在页面执行任意代码 | 只新增 `adapters/<slug>`、配置、registry 注册和契约测试，通用 router、数据库表和页面无需平台分支 |
| REQ-06 | 遵守企业级工程规范 | 分层目录、锁定依赖、迁移、审计、日志脱敏、CI、许可证和无源项目构建门禁全部通过 |

## 3. 目标架构

```text
外部客户端
    │  https://gateway.example/v1 + sk-a2a-...
    ▼
All2API
├─ web/                         管理控制台
├─ services/api/app/            FastAPI 装配和 HTTP 层
│  ├─ domain/                   渠道、账号、Key、错误等纯领域规则
│  ├─ application/              用例、事务、审计和授权编排
│  ├─ ports/                    Adapter/Provisioner/Repository 接口
│  ├─ adapters/<slug>/          平台私有协议、账号流程和映射
│  ├─ infrastructure/           HTTP、数据库、加密、浏览器 worker
│  └─ routers/                  认证、管理面和统一数据面
└─ services/api/tests/          unit/integration/contract/security/e2e
```

依赖方向固定为 `routers → application → domain ← ports ← adapters/infrastructure`。`domain` 不得依赖 FastAPI、httpx、SQLite、Playwright 或任何源项目包；router 和 Web 不得写 `if channel == ...`。

核心对象：

- `ChannelManifest`：稳定 slug、显示名、版本、协议、能力、配置 schema、账号 flow 和健康状态。
- `Account`：统一状态、渠道、脱敏 native id、配额、运行态和 `credential_ref`；平台字段只进版本化 `ext`。
- `GatewayKey`：哈希后的 Key、过期时间、RPM、`allowed_channels`、`allowed_models`。
- `UpstreamAdapter`：模型发现、调用、流式响应、错误映射和健康检查。
- `AccountProvisioner`：账号新增、主动导入、轮询、完成、取消、刷新和删除；不提供外部账号同步。

## 4. 对外调用和授权

默认 Base URL 为 `http://localhost:8080`，生产使用 HTTPS；数据面路径为 `/v1`。调用方只需要一把 All2API Key：

```bash
curl "${ALL2API_BASE:-http://localhost:8080}/v1/chat/completions" \
  -H "Authorization: Bearer $ALL2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"wb/cn:glm-5.2","messages":[{"role":"user","content":"hello"}]}'

curl "${ALL2API_BASE:-http://localhost:8080}/v1/chat/completions" \
  -H "Authorization: Bearer $ALL2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"doubao/doubao-pro","messages":[{"role":"user","content":"hello"}]}'

curl "${ALL2API_BASE:-http://localhost:8080}/v1/chat/completions" \
  -H "Authorization: Bearer $ALL2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"chatgpt/gpt-4o-mini","messages":[{"role":"user","content":"hello"}]}'
```

Key 创建示例（目标契约，当前 validator 若尚未支持按渠道 wildcard，需先完成对应迁移）：

```http
POST /admin/api/keys
```

```json
{
  "name": "team-a",
  "channels": ["wb", "chatgpt"],
  "models": ["wb/*", "chatgpt/gpt-4o-mini"],
  "limit_rpm": 60,
  "expires_at": null
}
```

`channels=[]` 代表全部当前已启用且已配置渠道；Key 明文只在创建或轮换响应中返回一次。请求流程必须先解析 Key，再校验渠道和模型 scope，最后才允许 scheduler 选择账号。别名展开后对每个实际目标再次校验，不能借此绕过授权。

## 5. 新增账号：先选渠道，再执行渠道方法

统一流程如下：

```text
选择 channel
  → 读取该 channel 的 provision-schema
  → 选择 flow 并提交动态 payload
  → start / poll / complete 或 import / cancel
  → CredentialStore 加密保存
  → 归一化 Account、审计、刷新模型目录
```

这里的 `import` 是管理员主动提交本次新增账号的凭据材料；账号目录不会从三个源项目或其他外部
服务同步。旧的 `/admin/api/accounts/sync` 已删除，账号列表只来自本项目的 provision 结果。

第一步只能选择已注册渠道；未选择渠道时不展示平台字段。通用账号服务只负责校验 channel/flow/schema、幂等、TTL、审计和持久化，不认识 `realm`、`account_id`、`callback`、`access_token` 等平台字段。

三个来源项目的新增账号能力需要迁入本项目对应 adapter/provisioner，方法映射如下：

| 渠道 | 来源方法（只读迁移输入） | All2API 目标方法 | 迁移要求 |
|---|---|---|---|
| WorkBuddy | `server/routers/accounts.py` 的 `/api/auth/start`、`/api/auth/poll`；`server/services/tencent.py:start_login/poll_login/write_auth_file` | `adapters/workbuddy/provisioner.py` 的 `start/poll/complete` | 保留 realm、二维码、token 轮换和账号归一化语义；凭据改写入本项目 CredentialStore，不复制 `data/auths` |
| Doubao | `src/auth/account_manager.py:add_account`；`src/auth/qr_login.py:QRLogin`；`src/server/unified_server.py` 管理接口 | `adapters/doubao/provisioner.py` 的 `create_profile/qr_login` | 保留 profile 创建、二维码轮询和 Cookie 注入；浏览器上下文由本项目 worker 管理，不读取源 `data/accounts` |
| ChatGPT | `api/accounts.py` 的账号导入/OAuth 路由；`services/account_service.py:add_accounts/add_account_items`；`services/oauth_login_service.py:OAuthLoginService.start/finish` | `adapters/chatgpt/provisioner.py` 的 `token_import/oauth_pkce` | 保留 token 三件套、PKCE、去重和刷新语义；token 只写入加密存储，不调用源项目 API |

这里的“引入方法代码”指把可迁移的协议和业务行为重写/改造到目标 adapter；不允许通过 Python import、HTTP、文件共享或进程调用把源项目包装成长期依赖。每个迁移项必须登记源版本、文件/符号、许可证、改写范围、fixture、测试和负责人。

## 6. 新平台扩展位置

新增平台必须创建以下代码边界：

```text
services/api/app/adapters/<slug>/
├─ manifest.py       # 渠道身份、能力、配置和 flow schema
├─ adapter.py        # health/list_models/invoke/invoke_stream/map_error
├─ provisioner.py    # start/poll/complete/import/cancel/refresh
├─ schemas.py        # 平台输入输出校验
├─ mapper.py         # 平台对象 → canonical Account/Model/Usage
├─ errors.py         # 平台错误 → ErrorKind
└─ tests/contract/   # 脱敏 fixture、状态机和协议契约
```

然后在 registry 注册、补充配置/Secret schema、数据库迁移（如确有必要）、告警和文档。禁止在通用 router、application、数据库表或前端组件新增平台专用分支；如果确需修改核心，必须证明它是所有渠道共有的 port/领域规则并提交 ADR。

## 7. 当前代码和迁移停止线

当前 checkout 仍保留 bridge 过渡实现：`app/adapters/{wb,chatgpt,provisioning}.py`、
`app/adapters/doubao_transport.py` 会访问迁移期配置，`routers/admin.py` 仍有兼容分支；
bridge 默认关闭。三渠道 native provisioner、二维码会话、加密凭据和本地账号目录已接入，
但兼容模块只能用于行为对照和迁移联调，不能作为新渠道模板。

迁移完成前不得声明渠道 `built_in=true`。每个渠道必须同时完成：内置 client/worker、账号新增与刷新、模型和调用、Key scope、contract/integration/E2E、安全扫描、OpenAPI/配置/运维文档，以及源项目不可用时的 clean build/run。

## 8. 开发顺序和完成定义

1. **M0 基线**：冻结契约、审计来源、许可证和脱敏 fixture。
2. **M1 内核**：完成 domain/ports、registry、Key 授权、账号状态机和 fake adapter。
3. **M2-M4 渠道内置**：按 WorkBuddy、Doubao、ChatGPT 完成 provisioner、凭据、client/worker 和协议。
4. **M5 切换**：关闭 bridge，停止源项目，执行无源项目验证并导入经确认的账号。
5. **M6 扩展证明**：加入 fake/new adapter，证明通用 API、页面和数据库不需平台分支。

完成定义：前端 lint/typecheck/build、后端 ruff/pytest、迁移和许可证检查通过；删除或隔离三个源项目后仍能安装、构建、测试、启动；三渠道均能通过同一 URL + Key 调用；账号新增先选渠道；未授权渠道稳定返回 403；日志、数据库、前端 bundle 和产物无明文凭据与源路径。
