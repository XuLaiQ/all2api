# 目录重构与迁移映射

本文把当前过渡代码映射到企业级目标目录，避免开发者把现有扁平模块误认为最终架构。迁移期间允许兼容运行，但新功能必须落在目标边界内。

## 1. 当前到目标的映射

| 当前路径 | 当前职责 | 目标路径 | 迁移动作 | 停止扩展条件 |
|---|---|---|---|---|
| `services/api/app/main.py` | FastAPI 装配 | `app/main.py` + `app/infrastructure/bootstrap.py` | 保留入口，拆出依赖注入和启动生命周期 | 不在入口写渠道分支 |
| `services/api/app/config.py` | 环境配置 | `app/infrastructure/config/` | 配置 schema 按服务/渠道版本化 | 不新增旧 `A2A_*_UPSTREAM_*` 必填项 |
| `services/api/app/db.py` | SQLite schema、过渡仓储 | `app/infrastructure/persistence/` + `app/ports/repositories.py` | 把 SQL/事务与领域实体分离，补迁移版本 | domain/application 不得 import db.py |
| `services/api/app/security.py` | 管理会话和 Key hash | `app/infrastructure/security/` + `app/application/keys/` | 保留安全算法，抽出用例和审计 | 不把渠道授权写进 adapter |
| `services/api/app/routers/admin.py` | 管理 HTTP 和账号分支 | `app/routers/admin.py` + `app/application/*` | router 只做 schema、权限、响应；用 registry dispatch | 禁止继续增加 `if channel == ...` |
| `services/api/app/adapters/wb.py` | WorkBuddy HTTP bridge | `app/adapters/workbuddy/` | 重写为内置 client、mapper、manifest、provisioner | 不再访问源项目端口或管理 API |
| `services/api/app/adapters/doubao.py`（已删除） | Doubao HTTP bridge | `app/adapters/doubao/` + `browser.py` | 已拆为本项目 profile、QR 状态机和浏览器 worker | 不读取源 `data/accounts` |
| `services/api/app/adapters/chatgpt.py` | ChatGPT HTTP bridge | `app/adapters/chatgpt/` | 内置 OAuth/token/client，凭据走 CredentialStore | 不调用源项目 API |
| `services/api/app/adapters/provisioning.py` | 三渠道统一 HTTP 代理 | `app/ports/provisioning.py` + 各渠道 `provisioner.py` | 先由 application 调 port，再删除 bridge | 迁移完成后不得成为新增渠道模板 |
| `services/api/app/scheduler/` | 过渡账号池和运行态 | `app/application/gateway/` + `app/scheduler/` + ports | 保留跨渠道调度，账号私有能力由 adapter 提供 | 不让 adapter 决定 Key scope |
| `services/api/app/protocols/` | 入站协议转换 | `app/application/gateway/protocols/` | 与上游 adapter 解耦，按 manifest 能力校验 | 不把平台字段泄露到公共 DTO |
| `web/src/features/accounts/` | 三渠道固定新增表单 | `web/src/features/accounts/` schema renderer | 改为 channel → manifest → 动态 flow | 不新增平台专用组件分支 |

## 2. 目标目录模板

```text
services/api/app/
├─ domain/
├─ application/
├─ ports/
├─ adapters/
│  ├─ registry.py
│  ├─ workbuddy/
│  ├─ doubao/
│  ├─ chatgpt/
│  └─ <new-platform>/
├─ infrastructure/
│  ├─ http/
│  ├─ browser/
│  ├─ persistence/
│  ├─ crypto/
│  └─ workers/
├─ routers/
└─ scheduler/
```

测试目录和目标目录一一对应：`tests/unit` 验证领域与用例，`tests/integration` 验证存储/迁移，`tests/contract/<slug>` 验证适配器，`tests/security` 验证 Secret/Key/权限，`tests/e2e` 验证页面和完整流程。

## 3. 分阶段迁移顺序

### 阶段 A：内核先行

- 建立 `domain`、`application`、`ports` 和 registry；
- 将 Key 的 `channels/models` scope、账号状态机、provision session 和审计放入通用用例；
- 注册 fake adapter，证明核心不依赖具体平台；
- bridge 增加兼容标记并默认关闭，不能污染目标配置。

### 阶段 B：逐渠道内置

按 WorkBuddy → Doubao → ChatGPT 迁移。每个渠道先迁账号凭据生命周期，再迁模型目录和调用，最后迁多媒体/优化能力。每项迁移都先写脱敏行为 fixture，再写实现和契约测试。

### 阶段 C：切换和清理

- 将用户确认的账号信息通过显式 import 导入本项目；
- 停止 bridge、源项目端口和源项目容器；
- 删除运行时代码中的源路径、旧端口、外部管理 token 和桥接变量；
- 在没有三个源目录的 clean checkout 中重新安装、构建、测试和启动。

## 4. 合并停止线

以下任一项未满足，PR 不得标记迁移完成：

- 运行时代码仍 import 源项目包或访问其 URL/端口；
- 账号新增仍由 `provisioning.py` 转发到源项目；
- router、application 或 Web 出现新的平台 `if/elif`；
- 凭据写入普通 SQLite 字段、日志、响应或前端状态；
- 缺少对应 adapter contract、错误矩阵、幂等/取消/过期测试；
- 没有更新 OpenAPI、配置示例、迁移矩阵、运维说明和回滚说明；
- 未通过三源目录不可用时的 clean build/run。

## 5. 每个迁移 PR 必填内容

```text

源项目/版本/文件/符号：

目标模块：
凭据和数据影响：

contract/integration/e2e 测试：
许可证与依赖审查：
回滚和兼容策略：
无源项目验证证据：
```
