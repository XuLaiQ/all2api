# 前端开发准备

全项目的需求边界、API 契约、安全、测试和交付门槛见[项目开发基线](项目开发基线.md)与[API 契约](API契约.md)。本文只维护 Web 工程的专属约定。

## 目标与边界

前端是 All2API 的统一渠道管理控制台，管理 WorkBuddy、doubao、chatgpt 三个基线渠道，并为后续已注册适配器动态提供相同管理入口。它同时配置网关调用者的 API Key、模型与路由；调用方最终只需使用统一 Gateway Base URL 和网关 Key。当前登录、运行总览、用量统计、请求日志、网关密钥、模型目录、路由规则、渠道状态和账号池只读快照页面已接入 FastAPI。M5-1 已提取原型浅色令牌、重做分组侧栏与顶栏，并把总览重排为真实 KPI、每日请求趋势和渠道状态；逐页样式仍在按原型迭代。账号操作、渠道配置编辑和设置页面仍按 M4-M5 阶段推进。后端 FastAPI 与 SQLite 是业务事实来源，浏览器只保留界面状态与必要的临时输入。

## 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| UI | React 19 + TypeScript 5.7 strict | 对齐参考项目的 React / TypeScript 主线 |
| 构建与开发服务器 | Vite 6 + `@vitejs/plugin-react` | 沿用参考项目 desktop 的 Vite 配置模式；本项目明确使用浏览器 SPA |
| 路由 | React Router 7 | 声明式路由、嵌套路由与后续鉴权边界 |
| HTTP | Axios 1.x，`web/src/api/client.ts` | 集中 base URL、超时、Cookie 会话和错误归一化 |
| 包管理 | pnpm 10 workspace | 沿用参考项目 workspace 与递归脚本 |
| 代码质量 | ESLint 9 flat config、typescript-eslint、React Hooks 规则 | `lint`、`typecheck` 作为合并前门禁 |

参考项目的 web 客户端位于 `apps/web` 并使用 Next.js；本项目将前端直接放在仓库根目录的 `web/`，选择 Vite SPA，以满足明确提出的 React Router 与 Axios 客户端架构。管理控制台依赖登录会话、表格筛选和操作交互，没有 SSR/SEO 需求；pnpm workspace、严格 TS 配置和 Vite 插件模式沿用参考项目已有实践。

不在前端放置上游 API Key、管理令牌、数据库地址或服务端 Secret。登录会话采用服务端设计的 HttpOnly Cookie；前端不得自行决定权限，所有写入仍由 `/admin/api` 重新鉴权。

## 依赖清单

运行依赖：`react`、`react-dom`、`react-router-dom`、`axios`。

开发依赖：`vite`、`@vitejs/plugin-react`、`typescript`、React/Node 类型包、`eslint`、`@eslint/js`、`typescript-eslint`、`eslint-plugin-react-hooks`、`eslint-plugin-react-refresh`、`globals`。

根目录维护单一 `pnpm-lock.yaml`。不直接修改 lockfile；增加/移除依赖后运行 `pnpm install` 并提交 lockfile。后续按需求评估 UI 组件库、图表、表格、表单校验和 E2E 工具，不提前引入未用依赖。

## 环境变量与运行配置

`web/.env.example` 是浏览器端配置模板，复制为 `.env.local`：

| 变量 | 默认值 | 用途 |
|---|---|---|
| `VITE_PROXY_TARGET` | `http://127.0.0.1:8080` | Vite 将 `/admin/api` 与 `/v1` 代理到 FastAPI |
| `VITE_ADMIN_API_BASE_URL` | `/admin/api` | 管理面 Axios base URL；同源代理避免本地 CORS |

所有 `VITE_*` 值都会进入浏览器构建产物，只允许公开地址或开关。服务端配置见 `services/api/.env.example`。本地 API 默认端口 8080；前端 dev server 为 `http://localhost:5173`，预览端口为 4173。端口占用时显式调整 Vite 配置和后端 `A2A_CORS_ORIGINS`。

## 目录结构

```text
web/
├── src/
│   ├── app/                 # 应用壳、全局错误边界、导航与布局
│   ├── api/                 # Axios 实例、统一错误类型与 API 调用入口
│   ├── components/          # 跨功能复用的基础 UI 组件
│   ├── features/            # overview、channels、accounts、keys、routes、logs、audit、settings 等业务模块
│   ├── hooks/               # 跨功能 React hooks
│   ├── router.tsx           # 路由树与懒加载边界
│   ├── main.tsx             # SPA 入口
│   └── styles.css           # 全局 reset 与设计令牌入口
├── .env.example
├── eslint.config.js
├── tsconfig.json
└── vite.config.ts
```

一个功能的页面、局部组件、API hooks 与 DTO 靠近放在 `features/<name>/`；只有确实跨功能复用后再提升到 `components/`。API 请求不得散落在组件中。

## 安装与启动

环境要求：Node.js 20.19+（建议使用当前 LTS）与 pnpm 10。仓库根目录执行：

```powershell
pnpm install
Copy-Item web/.env.example web/.env.local
pnpm dev:web
```

浏览器打开 `http://localhost:5173`。后端就绪后，在另一个终端启动：

```powershell
cd services/api
uv sync
uv run uvicorn app.main:app --reload --port 8080
```

日常提交前执行 `pnpm lint`、`pnpm typecheck` 和 `pnpm build`。完整页面验收按 `docs/系统设计与实现文档.md` M5 与 `docs/页面高度与滚动条开发规则.md` 执行。

## 开发规范

- TypeScript strict；避免 `any`，边界数据使用 `unknown` 并校验。
- 页面通过 React Router 管理；业务模块按 feature 组织，组件保持单一职责。
- 所有 HTTP 请求经过 `web/src/api/client.ts`；统一处理超时、会话 Cookie、HTTP 错误、加载态、空态和失败态。
- API DTO 以管理 API 契约为准；请求/响应契约变化时同步更新共享类型与文档，不在 UI 猜字段含义。
- 后端是唯一业务事实来源；localStorage 不存业务数据或凭据。只有经过安全设计评审的短期偏好才可持久化。
- 不在组件中硬编码 API URL、令牌、渠道/模型枚举；可扩展选项由后端注册表提供。
- 所有路由页面适配键盘操作和窄视口；页面高度、内部滚动与验证遵循 `docs/页面高度与滚动条开发规则.md`。
- 布局滚动边界：桌面应用壳使用 `100dvh`，仅 `.page-stage` 承担主内容纵向滚动；820px 以下解除壳锁高并恢复自然文档滚动。弹窗仅编辑面板自身纵向滚动。每个路由和目标视口仍需按页面高度规则记录 DOM 探针数据后，才能标记布局验收通过。
- 每个 PR/变更同步说明影响范围、验证命令和 API/设计文档变化； lint、类型检查、构建均通过后才进入验收。

## 后续开发步骤

1. M1：以 WorkBuddy 验证管理适配器、模型列表和统一 `GET /v1/models` / `POST /v1/chat/completions` 的端到端契约。
2. M2-M3：接入 doubao 与 chatgpt；此阶段结束前必须能在同一个控制台管理三家，并用同一 Gateway Base URL + 网关 Key 调用三家模型。随后补齐账号、密钥、模型/路由及计量接口。
3. M4：完成管理面 API 与权限矩阵，确认九个页面需要的字段、操作、确认流程及失败恢复行为。
4. M5-1：把 HTML 原型拆成设计令牌、布局、导航和基础组件；先完成路由骨架与总览页。
5. M5-2：按总览、渠道、账号池、密钥、模型/路由、请求日志、用量统计、调试台和设置逐页实现；三家渠道使用同一组通用页面与 API 契约，不为平台复制页面。
6. M5-3：按页面高度规则对各路由和目标视口做布局检查，验证权限、写操作确认、会话过期与网络失败恢复。
7. M5-4：完成三渠道统一 URL/API Key 调用验收、真实服务端到浏览器端到端验收、数据对账和构建产物检查；再增加一个测试适配器证明通用管理页面可扩展，并更新文档与交付记录。
