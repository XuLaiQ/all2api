# 目标架构与迁移方案

> 状态：目标架构基线
>
> 本文是本项目“融合而不依赖源项目”的最高优先级说明。若旧文档仍出现“网关通过 HTTP 调用三个独立反代”的表述，以本文目标态和[项目开发基线](项目开发基线.md)为准；那种方式只能存在于迁移期兼容 profile。

## 1. 不可歧义的目标

`all2api` 是唯一源码、唯一构建、唯一部署交付物。WorkBuddy、Doubao、ChatGPT 三个现有项目只提供一次性迁移输入：代码审计、行为样本、协议 fixture 和缺陷记录。

目标态不得通过以下任何方式依赖源项目：

- Python/Go import、Git submodule、相对路径或动态 `sys.path`；
- HTTP/IPC 请求源项目端口；
- 读取源项目数据库、`data` 目录、账号文件、Cookie、OAuth token 或浏览器 profile；
- 启动源项目的脚本、二进制、容器或 compose service；
- 把源项目的环境变量名作为目标态必填配置；
- 在日志、构建产物、OpenAPI 或前端 bundle 中泄露源目录绝对路径。

目标态允许内部使用浏览器 worker、平台专用 worker 或 Go/Python 子进程，但这些组件必须在本仓库中拥有源码、锁定依赖、Dockerfile/启动方式、健康检查和测试。统一项目不等于强制单进程；它要求统一源码归属和生命周期。

## 2. 术语和边界

| 术语 | 定义 |
|---|---|
| 渠道 Channel | 一个可独立配置、管理账号、发现模型并执行请求的平台接入，如 `wb`、`doubao`、`chatgpt` |
| 适配器 Adapter | 实现渠道私有协议、能力、错误映射和凭据流程的代码包 |
| 平台上游 | WorkBuddy/Doubao/ChatGPT 官方服务或网页；它是业务网络依赖，不等于三个源反代项目 |
| bridge profile | 迁移期间临时把旧 HTTP 服务接入网关的兼容配置；目标开关默认关闭，不计入最终验收 |
| 内置渠道 | 代码和依赖已进入本仓库，源目录断开后仍可运行的渠道 |
| 账号凭据 | access/refresh/id token、Cookie、浏览器 profile、device token 等敏感材料；只能由 CredentialStore 管理 |

## 3. 目标拓扑

```text
外部客户端
    │ 统一 https://gateway.example/v1 + sk-a2a-* 
    ▼
all2api 交付物
├─ web（管理控制台）
├─ gateway-api（/v1 与 /admin/api）
├─ application（路由、Key、账号、审计、计量用例）
├─ domain + ports（与平台无关的规则和 SPI）
├─ adapters/workbuddy       ─┐
├─ adapters/doubao           ├─ 内置平台客户端/worker → 官方平台
├─ adapters/chatgpt         ─┘
├─ scheduler + repositories
└─ SQLite + 加密 CredentialStore + 运行态
```

外部源项目不出现在拓扑中。Doubao 的 Chromium profile 放在本项目受控数据目录；WorkBuddy 的原 Go 账号池能力可重构为本项目 worker；ChatGPT 的 `curl_cffi`、OAuth/PoW/Sentinel 能力作为本项目 adapter 依赖锁定。

## 4. 分层和依赖方向

```text
presentation (web/routers)
        ↓
application (use cases)
        ↓
domain (entities, policies, errors)
        ↓
ports (Adapter, Provisioner, Repository, CredentialStore)
        ↑
adapters + infrastructure (HTTP, browser, SQLite, crypto)
```

规则：

1. `domain` 不得 import FastAPI、httpx、SQLite、Playwright、curl_cffi 或平台 SDK。
2. `routers` 只依赖 application service；不得出现 `if channel == ...`、具体平台 URL 或凭据读取。
3. `application` 通过 ports 调用渠道，不直接构造平台客户端。
4. adapter 只实现一个渠道的私有行为，不决定跨渠道优先级、Key 授权或全局重试。
5. Web 只消费 manifest/schema，不硬编码渠道枚举和渠道字段。
6. 配置、数据库、加密和浏览器生命周期通过依赖注入装配，禁止模块导入时产生副作用。

## 5. 核心领域模型

### 5.1 Channel

```text
id/slug, display_name, adapter_version, enabled,
protocols[], capabilities[], account_flows[], config_schema_version,
health_state, created_at, updated_at
```

`slug` 是稳定外部标识，发布后不可随意改名。模型、Key scope、路由目标和审计日志均引用 slug。

### 5.2 Account

```text
id, channel, native_id_hash, display_name, kind, tier,
status, enabled, quota, expires_at, runtime_state,
credential_ref, ext, created_at, updated_at
```

统一表只保存可比较字段和加密凭据引用；平台字段进入版本化 `ext`，不得把 token、Cookie、profile 路径放入 `ext`。`native_id` 对外脱敏，必要的原值只在 adapter/credential store 内部使用。

### 5.3 GatewayKey

```text
id, prefix, key_hash, enabled, expires_at,
allowed_channels[], allowed_models[], rpm, created_at, last_used_at
```

Key 明文仅在创建或轮换响应返回一次。请求解析出渠道后，必须同时通过渠道和模型授权；路由 alias 展开后对每个实际目标重新校验。

## 6. 运行请求流程

1. gateway 解析 Bearer 或 `x-api-key`，查找哈希 Key。
2. 规范化模型 ID：`<channel>/<model>` 或 alias；拒绝含糊的同名模型。
3. application service 校验 Key 的 channel/model scope、限流、过期和渠道启用状态。
4. scheduler 依据渠道能力、模型可用性、账号状态、租约和冷却选择目标。
5. 通过 `UpstreamAdapter` 将标准请求转换为渠道请求，调用内置 client/worker。
6. adapter 将响应、SSE、usage 和错误映射为 canonical 结果；网关记录 request_id、channel、model、account（可信时）、延迟和计量。
7. 只在请求尚未开始向客户端发送流之后才允许按规则重试/降级；流已开始不得重放。

## 7. 三渠道迁移策略

| 渠道 | 迁入能力 | 目标模块 | 必须重构的边界 |
|---|---|---|---|
| WorkBuddy | realm、二维码 OAuth、JWT/device token、账号池、冷却/租约、SSE | `adapters/workbuddy/` + 可选 `workers/workbuddy/` | 不启动原 Go gateway；凭据写入 CredentialStore；池策略实现 ports |
| Doubao | 账号目录、浏览器 profile、QR 登录、Cookie/msToken/device、SSE/多媒体 | `adapters/doubao/` + `adapters/doubao/browser/` | Playwright 生命周期归本项目；禁止读取原 `data/accounts`；验证码/浏览器故障可隔离 |
| ChatGPT | OAuth PKCE、token 导入/刷新、Sentinel/PoW、模型目录、Responses/Chat | `adapters/chatgpt/` | token 与 plan 归一化；禁止复用原 storage/backend；外部请求经本项目 client |

迁移时只复制可审计的算法和协议行为，不复制账号数据、Cookie、OAuth token、浏览器 profile、运行态数据库或无关前端。每一项代码来源、版本、许可证、依赖许可证和改写记录都要登记在[三渠道代码迁移矩阵](三渠道代码迁移矩阵.md)。

## 8. 迁移阶段

### M0：基线和合规

- 冻结本项目目标 API、域模型和安全边界；
- 对三个源项目建立只读审计报告、版本/hash、许可证和依赖清单；
- 建立脱敏 fixture、mock 上游和 adapter contract tests；
- 给 bridge profile 加醒目标记，并新增默认关闭的总开关。

### M1：内核先行

- 建立 `domain/application/ports/infrastructure` 目标目录；
- 将 registry 从 URL/key 描述升级为 manifest + adapter + provisioner；
- 将 Key channel/model scope、统一路由和账号状态机落到核心；
- fake adapter 必须可在不改核心的情况下完成模型、账号和调用测试。

### M2-M4：逐渠道内置

按 WorkBuddy → Doubao → ChatGPT 顺序迁移。每个渠道必须先完成账号凭据生命周期，再接入模型/聊天，最后接入多媒体和优化；不得把旧 HTTP wrapper 直接视为迁移完成。

### M5：切换与清理

- 导入经用户确认的账号信息；原始凭据不从源目录批量复制；
- 关闭 bridge profile、源端口和源项目容器；
- 运行无源项目构建/测试/启动门禁；
- 删除目标代码中的旧环境变量和兼容分支，或明确标为仅迁移工具。

### M6：横向扩展证明

加入一个 fake/test adapter，验证只增加 adapter 包、manifest、配置和契约测试，通用渠道、账号、Key、路由、日志和 UI 自动获得能力。

## 9. 回滚与兼容

M0 需要新增 `A2A_LEGACY_BRIDGE_ENABLED=false`（目标默认值）控制旧 bridge；当前
checkout 尚未实现该开关。bridge 只能用于开发和数据对照：

- 不得写入目标生产凭据；
- 不得让新平台依赖 bridge；
- 日志必须标记 `compatibility_mode=legacy_bridge`；
- 最终发布前必须移除或隔离 bridge 模块；
- 回滚只回滚 adapter 版本/feature flag，不回滚数据库中已哈希的 Key 或已审计事件。

## 10. 目标态配置原则

目标配置按渠道命名但描述**内置客户端**，例如浏览器可执行文件、官方 API base、OAuth client id、加密存储 key、worker 并发；不得要求 `A2A_WB_UPSTREAM_BASE`、`A2A_DOUBAO_UPSTREAM_BASE`、`A2A_CHATGPT_UPSTREAM_BASE` 或外部管理 token。所有 Secret 通过 SecretStr/密钥管理系统注入，不写入镜像和 Git。

## 11. 完成判定

只有同时满足以下条件，渠道才可标记 `built_in=true`：

- 源项目目录、端口、进程和数据库均不可用时，渠道仍能启动；
- 账号新增、刷新、禁用、删除和同步由本仓库代码执行；
- 同一 `/v1` + Key 能按 scope 调用该渠道；
- adapter contract、集成、E2E、安全和许可证检查通过；
- 文档、OpenAPI、配置模板、迁移记录和运维告警已更新。
