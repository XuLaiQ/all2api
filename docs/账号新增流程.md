# 账号新增流程

本文规定管理面“新增账号”的统一行为。核心原则是：**先选择渠道，再读取该渠道能力并选择新增方式**。账号新增不是一个把三套表单堆在一起的通用接口，也不是调用旧项目 HTTP 接口的永久代理。

> 状态：目标规范。当前实现尚未满足本规范，实际差距见第 9 节；后续开发必须以本规范
> 为验收基线，而不能把现有 bridge 行为当成完成状态。

## 1. 用户流程

```text
打开新增账号
  ↓
GET /admin/api/channels
  ↓
选择已注册且已配置的 channel
  ↓
GET /admin/api/channels/{channel}/provision-schema
  ↓
选择 flow，按 schema 展示动态字段
  ↓
POST .../provision/start（需要幂等键）
  ↓
按 session 状态轮询或提交回调/import
  ↓
凭据安全落盘 → normalize Account → 审计 → 刷新模型/账号快照
```

未选择渠道时不展示平台字段、不允许提交；切换渠道时必须清空前一个 flow 的表单和会话。前端只渲染 schema，不写 `wb/doubao/chatgpt` 专用业务分支。

## 2. 管理 API 契约

### 2.1 获取渠道和流程

```http
GET /admin/api/channels/{channel}/provision-schema
```

响应示例：

```json
{
  "data": {
    "channel": "chatgpt",
    "adapter_version": "1.0.0",
    "flows": [
      {
        "id": "oauth-pkce",
        "kind": "oauth",
        "schema": {
          "type": "object",
          "properties": {"email_hint": {"type": "string", "maxLength": 256}}
        },
        "supports": {"start": true, "poll": false, "complete": true, "cancel": true},
        "timeout_seconds": 600,
        "requires_admin": true
      }
    ]
  }
}
```

### 2.2 开始、轮询、完成、导入和取消

推荐目标路径如下；迁移期可保留现有 `/accounts/{channel}/onboarding/*` 作为兼容别名，但两者必须调用同一个 provisioner：

```http
POST /admin/api/channels/{channel}/accounts/provision/start
GET  /admin/api/channels/{channel}/accounts/provision/{session_id}
POST /admin/api/channels/{channel}/accounts/provision/{session_id}/complete
POST /admin/api/channels/{channel}/accounts/provision/import
POST /admin/api/channels/{channel}/accounts/provision/{session_id}/cancel
```

请求 envelope：

```json
{
  "flow": "qr-oauth",
  "payload": {"realm": "cn", "region": ""},
  "idempotency_key": "acc_01J..."
}
```

约定：

- `channel` 来自 URL 且必须已注册；body 不接受第二个可冲突的 channel；
- `payload` 只允许 manifest schema 声明的字段；未知字段返回 `422`；
- `idempotency_key` 必填，重放同一操作返回同一会话/结果，不重复写凭据；
- 响应只返回 session id、下一步、脱敏账号信息和状态，不返回 token、Cookie、profile 内容或原始上游响应；
- 所有写操作要求 `admin`，每次 start/complete/import/cancel 写审计事件；
- 会话必须有过期时间、最大轮询频率、取消语义和失败后的可重试策略。

## 3. 统一状态机

```text
created → waiting_user → waiting_callback/polling → validating
       → storing → succeeded
       ├→ expired
       ├→ cancelled
       ├→ failed_retryable
       └→ failed_terminal
```

状态转换由 application service 校验，adapter 只能报告平台事件。重复 complete、过期 session、错误 channel、凭据校验失败和并发冲突分别映射到 `409`、`410`、`404`、`422` 或 `502/504`，具体错误码写入 OpenAPI。

## 4. 三渠道内置流程

### 4.1 WorkBuddy

迁移行为：二维码 OAuth `start → poll`，支持 `cn/global` realm 和 global 地区；授权完成后提取 uid、nickname、enterprise/realm、access/refresh token、expiresAt 和 device token。

目标实现：

- `adapters/workbuddy/provisioner.py` 实现 `qr-oauth` flow；
- `CredentialStore.atomic_write()` 或加密记录保证凭据原子写入，不能使用半成品文件；
- realm/region 作为 schema 字段校验，不散落在 router；
- token 刷新、过期、撤销和账号池状态由 WorkBuddy adapter 管理；
- 不启动原项目 Go gateway，不复制原 `data/auths` 文件。

### 4.2 Doubao

迁移行为：先创建账号 profile/meta，再开始指定账号 QR 登录；二维码状态由浏览器/HTTP 客户端轮询，成功后收集 Cookie、msToken、device/fp 等会话材料并注入 Playwright context。

目标实现：

- `adapters/doubao/provisioner.py` 提供 `create-profile` 和 `qr-login` 两个 flow；
- profile 根目录由本项目配置决定，路径不得来自源项目；
- browser worker 的启动、并发、关闭、崩溃恢复和验证码状态可观测；
- cookies/session 只存 CredentialStore 或受 ACL 保护的 profile，不进 API 响应、SQLite 普通字段或日志；
- 不调用原项目 `/admin/api/accounts` 或 `/v1/session/qr-login`。

### 4.3 ChatGPT

迁移行为：支持 access token/完整 token 三件套导入，也支持 OAuth PKCE `start → callback/finish`；完成后校验 token、归一化 plan/source_type 并刷新模型目录。

目标实现：

- `adapters/chatgpt/provisioner.py` 提供 `token-import`、`oauth-pkce`；
- access/refresh/id token 加密存储，refresh 过程使用 per-account lock；
- callback 只允许一次完成，校验 state/PKCE、过期时间和 redirect 来源；
- OAuth client secret、token 和上游错误均不得返回前端；
- 不调用原项目 `/api/accounts/oauth/*` 或 `/api/accounts`。

## 5. 凭据与数据安全

| 数据 | 存储 | API/UI | 日志 |
|---|---|---|---|
| Gateway API Key | 哈希 | 创建/轮换时明文一次 | 仅 prefix/key_id |
| WorkBuddy token | 加密 CredentialStore | 不返回 | 禁止 |
| Doubao Cookie/profile | 加密引用或受控目录 | 不返回 | 禁止 |
| ChatGPT token | 加密 CredentialStore | 不返回 | 禁止 |
| session/callback | 短期加密/哈希状态 | 仅脱敏状态 | 不记录原文 |

账号列表只返回 canonical 字段和安全的 `ext`；原生 id 需要脱敏或仅供内部关联。删除账号时先撤销/销毁凭据，再删除索引，失败必须可重试并写审计。

## 6. 幂等、轮询和失败处理

- start/import 使用业务幂等键，数据库唯一约束保证并发下不重复创建；
- poll 使用指数退避和 `Retry-After`，服务端限制最小轮询间隔；
- 用户关闭页面不等于自动取消，必须提供显式 cancel 或 session TTL 清理；
- 网络超时可以重试，授权拒绝、验证码、凭据无效必须提示用户动作；
- complete 成功写入凭据但同步模型失败时，账号状态为 `ready_with_sync_pending`，由后台任务补偿，不重复登录；
- 所有异常响应统一错误 envelope，不透传平台 traceback/Secret/绝对路径。

## 7. 源代码迁移映射

三套源项目的新增账号行为、目标模块、许可证和 fixture 记录在[三渠道代码迁移矩阵](三渠道代码迁移矩阵.md)。迁移要求是“行为等价 + 接口重构”，不是把源项目接口包一层：源目录断开后，contract tests 必须仍可运行。

## 8. 前端验收

- 第一个可操作控件是渠道选择；无渠道时提交按钮禁用；
- 选择渠道后才加载 flow schema，加载/空/错误状态明确；
- 二维码、OAuth URL、callback、token import 均有过期、取消、重试和成功反馈；
- 切换渠道或关闭窗口不会泄露前一流程输入；
- 刷新账号列表后状态、审计和模型目录一致；
- 渠道新增后不修改页面代码即可出现其 flow。

## 9. 当前实现差距（2026-09-27）

当前代码已有账号新增弹窗和 `/accounts/{channel}/onboarding/*` 过渡接口，但尚未达到本规范：

| 位置 | 当前行为 | 目标改造 |
|---|---|---|
| `web/src/features/accounts/AccountOnboardingDialog.tsx` | 打开时自动选择第一个可用渠道，并按 `wb/doubao/chatgpt` 写死字段/轮询逻辑 | 初始 channel 为空；读取 manifest schema；通用 provision session renderer |
| `web/src/features/accounts/accountsApi.ts` | 调用 legacy onboarding path，DTO 固定三渠道字段 | 调用目标 provision API，payload 为 schema 驱动对象 |

| `services/api/app/adapters/provisioning.py` | 通过 HTTP 调用三个源项目的新增账号接口 | 拆到各内置 adapter 的 `provisioner.py`，使用本项目 CredentialStore/client/worker |

在上述四项完成且源项目不可用时三种 flow 仍通过 E2E 前，不得将“新增账号”标记为内置完成。
