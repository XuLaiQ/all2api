# 账号新增流程

本文规定管理面“新增账号”的统一行为。核心原则是：**先选择渠道，再读取该渠道能力并选择新增方式**。账号新增不是一个把三套表单堆在一起的通用接口，也不是调用旧项目 HTTP 接口的永久代理。

> 状态：四渠道 Go provisioner、二维码会话、加密凭据落库、本地账号目录和前端二维码渲染已实现；
> 真实平台账号 E2E 和凭据刷新闭环仍是发布门槛，差距见第 9 节。

## 1. 用户流程

```text
打开新增账号
  ↓
GET /admin/api/channels
  ↓
选择已注册且已配置的 channel
  ↓
GET /admin/api/channels/{channel}/provision-schema
  ↓
选择 flow，按 schema 展示动态字段
  ↓
POST .../provision/start（需要幂等键）
  ↓
按 session 状态轮询或提交回调/import
  ↓
凭据安全落盘 → normalize Account → 审计 → 刷新模型/账号快照
```

未选择渠道时不展示平台字段、不允许提交；切换渠道时必须清空前一个 flow 的表单和会话。前端只渲染 schema，不写 `wb/doubao/chatgpt` 专用业务分支。

## 2. 管理 API 契约

### 2.1 获取渠道和流程

```http
GET /admin/api/channels/{channel}/provision-schema
```

响应示例：

```json
{
  "data": {
    "channel": "chatgpt",
    "adapter_version": "1.0.0",
    "flows": [
      {
        "id": "oauth-pkce",
        "kind": "oauth",
        "schema": {
          "type": "object",
          "properties": {"email_hint": {"type": "string", "maxLength": 256}}
        },
        "supports": {"start": true, "poll": false, "complete": true, "cancel": true},
        "timeout_seconds": 600,
        "requires_admin": true
      }
    ]
  }
}
```

### 2.2 开始、轮询、完成、导入和取消

接口如下（旧的 `/admin/api/accounts/{channel}/onboarding/*` 兼容路径已删除）：

```http
POST /admin/api/channels/{channel}/accounts/provision/start
GET  /admin/api/channels/{channel}/accounts/provision/{session_id}
POST /admin/api/channels/{channel}/accounts/provision/{session_id}/complete
POST /admin/api/channels/{channel}/accounts/provision/import
POST /admin/api/channels/{channel}/accounts/provision/{session_id}/cancel
```

请求 envelope：

```json
{
  "flow": "qr-oauth",
  "payload": {"realm": "cn", "region": ""},
  "idempotency_key": "acc_01J..."
}
```

约定：

- `channel` 来自 URL 且必须已注册；body 不接受第二个可冲突的 channel；
- `payload` 只允许 manifest schema 声明的字段；未知字段返回 `422`；
- `idempotency_key` 必填，重放同一操作返回同一会话/结果，不重复写凭据；
- 响应只返回 session id、下一步、脱敏账号信息和状态，不返回 token、Cookie、profile 内容或原始上游响应；
- 所有写操作要求 `admin`，每次 start/complete/import/cancel 写审计事件；
- 会话必须有过期时间、最大轮询频率、取消语义和失败后的可重试策略。

`provision/import` 表示管理员主动提交本次新增账号所需的 token 或账号材料；它不读取、拉取或
同步任何外部项目的账号列表。项目已移除 `/admin/api/accounts/sync`，账号列表只来自本项目的
provision 流程写入的本地账号目录。

## 3. 统一状态机

```text
created → waiting_user → waiting_callback/polling → validating
       → storing → succeeded
       ├→ expired
       ├→ cancelled
       ├→ failed_retryable
       └→ failed_terminal
```

状态转换由 application service 校验，adapter 只能报告平台事件。重复 complete、过期 session、错误 channel、凭据校验失败和并发冲突分别映射到 `409`、`410`、`404`、`422` 或 `502/504`，具体错误码写入 [API 契约](API契约.md)。服务启动时会清理已过期且处于终态（succeeded/cancelled/expired/failed/failed_terminal）的 session 和过期的幂等记录；仍在进行中的 session 保留到流程自身报告过期。

## 4. 内置渠道流程

### 4.1 WorkBuddy

迁移行为：二维码 OAuth `start → poll`，支持 `cn/global` realm 和 global 地区；授权完成后提取 uid、nickname、enterprise/realm、access/refresh token、expiresAt 和 device token。

实现：

- `internal/adapters/workbuddy/provision.go` 实现 `qr-oauth` flow 和凭据刷新；`token-import` 由 `internal/application/accounts/provision.go` 处理；
- 凭据在 SQLite 事务内加密写入，不能使用半成品文件；
- realm/region 作为 schema 字段校验，不散落在 router；
- token 刷新、过期、撤销和账号池状态由 WorkBuddy adapter 管理；
- 不启动原项目 Go gateway，不复制原 `data/auths` 文件。

### 4.2 Doubao

行为：开始指定账号的 QR 登录；二维码状态由 HTTP 客户端或浏览器 worker 轮询，成功后收集 Cookie、msToken、device/fp 等会话材料。

实现：

- `internal/adapters/doubao/provision.go` 提供 `qr-login` flow；默认使用 `qr.go` 的 HTTP QR 客户端，`A2A_DOUBAO_BROWSER_ENABLED=true` 时改用 `browser_client.go` 调用 `cmd/doubao-browser-worker`（Chromium/CDP）；
- Cookie 导入走 `token-import` flow；
- profile 根目录由 `A2A_DOUBAO_PROFILE_ROOT` 决定，路径不得来自源项目；
- browser worker 的启动、并发、关闭、崩溃恢复和验证码状态可观测；
- cookies/session 只存 CredentialStore 或受 ACL 保护的 profile，不进 API 响应、SQLite 普通字段或日志；
- 不调用原项目 `/admin/api/accounts` 或 `/v1/session/qr-login`。

### 4.3 ChatGPT

迁移行为：支持 access token/完整 token 三件套导入，也支持 OAuth PKCE `start → callback/finish`；完成后校验 token、归一化 plan/source_type 并刷新模型目录。

实现：

- `internal/adapters/chatgpt/provision.go` 与 `oauth.go` 提供 `oauth-pkce` 和凭据刷新，`token-import` 由 `internal/application/accounts/provision.go` 处理；
- access/refresh/id token 加密存储，refresh 过程使用 per-account lock；
- callback 只允许一次完成，校验 state/PKCE、过期时间和 redirect 来源；
- OAuth client secret、token 和上游错误均不得返回前端；
- 不调用原项目 `/api/accounts/oauth/*` 或 `/api/accounts`。

### 4.4 Grok Web

迁移行为：管理员显式导入 Grok Web SSO token；调用前通过本地加密 CredentialStore 读取 token，必要时请求 Grok Session 接口解析 user id，再通过 WebSocket Gateway 建立临时会话。

实现：

- `internal/application/accounts/provision.go` 处理 `token-import` flow，接受 token 字符串或带 `user_id`、`tier`、Cloudflare cookie 元数据的账号对象；`provider=grok_build` 的条目按 Build OAuth 凭据保存；
- token、Cloudflare cookie 和 User-Agent 只加密写入凭据表，canonical account、模型目录、日志和审计不返回秘密；
- Grok 暂无凭据刷新接口，`POST /accounts/{id}/refresh` 返回 `501`；
- `internal/adapters/grok/client.go` 负责 `session.create`、`conversation.attached`、`conversation.item.create`、`response.create` 和 Gateway 流式事件转换；
- `basic`、`super`、`heavy` tier 只影响本地可见模型目录，不由 Key scope 或通用 gateway 决定；
- Console/Build 凭据、Imagine 图片/视频协议和浏览器清关没有迁移到当前 manifest，不得通过 Grok 文本渠道误调用。

## 5. 凭据与数据安全

| 数据 | 存储 | API/UI | 日志 |
|---|---|---|---|
| Gateway API Key | 哈希 | 创建/轮换时明文一次 | 仅 prefix/key_id |
| WorkBuddy token | 加密 CredentialStore | 不返回 | 禁止 |
| Doubao Cookie/profile | 加密引用或受控目录 | 不返回 | 禁止 |
| ChatGPT token | 加密 CredentialStore | 不返回 | 禁止 |
| Grok SSO token / Cloudflare cookie | 加密 CredentialStore | 不返回 | 禁止 |
| session/callback | 短期加密/哈希状态 | 仅脱敏状态 | 不记录原文 |

账号列表只返回 canonical 字段和安全的 `ext`；原生 id 需要脱敏或仅供内部关联。删除账号时先撤销/销毁凭据，再删除索引，失败必须可重试并写审计。

## 6. 幂等、轮询和失败处理

- start/import 使用业务幂等键，数据库唯一约束保证并发下不重复创建；
- poll 使用指数退避和 `Retry-After`，服务端限制最小轮询间隔；
- 用户关闭页面不等于自动取消，必须提供显式 cancel 或 session TTL 清理；
- 网络超时可以重试，授权拒绝、验证码、凭据无效必须提示用户动作；
- complete 成功写入凭据但模型目录刷新失败时，账号仍保持已落库状态，目录刷新由独立重试任务补偿，不重复登录；
- 所有异常响应统一错误 envelope，不透传平台 traceback/Secret/绝对路径。

## 7. 行为来源

各渠道的新增账号行为（协议、状态机、校验和映射）参考源项目后在本仓库重写，代码归本仓库所有；来源版本、文件/符号和许可证记录见 [`archive/python-era/三渠道代码迁移矩阵.md`](archive/python-era/三渠道代码迁移矩阵.md)。今后复制或改写外部代码，同样必须登记来源版本、文件/符号、许可证、修改范围和测试证据。

禁止把源项目作为库、HTTP 服务、子进程或共享目录引入：不得 import 源包、请求其管理 API、读取其账号目录/数据库、复制真实 Cookie/OAuth token/profile。

| 渠道 | Go 实现 | 必须保留的业务语义 |
|---|---|---|
| WorkBuddy | `internal/adapters/workbuddy/provision.go` | realm、二维码轮询、账号归一化、原子凭据写入和刷新 |
| Doubao | `internal/adapters/doubao/provision.go`、`qr.go`、`browser_client.go` + `cmd/doubao-browser-worker` | 账号隔离、二维码状态、Cookie 注入和取消；profile 目录由本项目控制 |
| ChatGPT | `internal/adapters/chatgpt/provision.go`、`oauth.go` | token 三件套导入、去重、PKCE state/verifier TTL、刷新和失败隔离 |
| Grok | `internal/application/accounts/provision.go`（导入）、`internal/adapters/grok/client.go` | SSO token 加密导入、tier 目录、WebSocket 会话和 SSE 转换 |

## 8. 前端验收

- 第一个可操作控件是渠道选择；无渠道时提交按钮禁用；
- 选择渠道后才加载 flow schema，加载/空/错误状态明确；
- 二维码、OAuth URL、callback、token import 均有过期、取消、重试和成功反馈；
- 切换渠道或关闭窗口不会泄露前一流程输入；
- 刷新账号列表后状态、审计和模型目录一致；
- 渠道新增后不修改页面代码即可出现其 flow。
